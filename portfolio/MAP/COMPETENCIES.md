## 역량별 근거

### 1. 문제 구조화

- 기능정의서의 user 서비스 요구사항 **17개**를 구현 상태와 대조한 gap 분석 → 팀 검증 체크리스트(V-B~V-L)의 뼈대가 됨 (개발 로그 §0.3)
- "날씨 변화 시 재추천"을 **감지(배치)·보관(스키마)·선택(API)·화면(배너)** 네 조각으로 나누고, 설계 결정 4개(재탐색 한도 차감 여부 · 자동 교체 여부 · 지난 일정 처리 · 무시 시 기준선)를 먼저 확정한 뒤 구현 (§24)
- 캐시 요구를 "중복 호출 방지"와 "조건 매칭 재사용" 둘로 분리. 사용자 간 캐시로 범위를 정하면서 인증 브랜치 병합과 무관하게 진행 가능해짐 (§0.5)

### 2. 실측 데이터 기반 의사결정

- 지하철·버스 필터 임계값을 **11개 지역 · 24개 구간 · 257건** 실측으로 0.80 산정. 오배제율 **1.6%** (§17, §21)
- 날씨 감시 쿼리를 `EXPLAIN (ANALYZE, BUFFERS)` 로 10만 건 재현 측정 — 부분 인덱스로 **약 41배**(16.0ms → 0.39ms), 버퍼 읽기 **97.4% 감소** (§25.1)
- 동기 재추천 엔드포인트로 앱의 API 왕복을 평균 **10~16회 → 1회** (실측 추천 소요 28~46초 기준, §25.1)

### 3. 디버깅 및 결함 재현

- 서울→부산 경로 **19건 중 19건(100%)** 이 "도보"로 표시되던 이동수단 매핑 누락을 재현·수정 (§18)
- 필터와 응답 절단의 순서 버그로 버스 검색 결과 **0건 → 8건** 복구 (§21)
- 재추천이 재사용 캐시에 걸려 agent가 돌지 않아 **날씨가 반영되지 않던 결함**을 코드 추적으로 발견·수정 (§24.2)
- 채팅 실시간 계층 결함 **6건** 발견 — 재연결 구간 메시지 유실, 좀비 연결, 비동기 교착으로 방 전환 정지 등 (§23)
- `loadLane` "실호출 계속 실패"의 원인이 API가 아니라 파라미터 형식임을 대조 실험으로 확정 — 접두사 누락 시 100% 재현, 부착 시 100% 성공 (§20)

### 4. 테스트 자동화

- 인증 도메인 초기 구현 시 테스트 **7개 파일 · 약 1,230줄** 동반 작성 (JWT · 카카오 OAuth · 레이트리밋 · REST Docs)
- 소켓 통로(`StreamChannel`)와 시계를 주입 가능하게 열어 장애 시나리오 **22건을 0.1초에** 재현. `fake_async` 가 `Stopwatch` 를 속이지 못함을 실험으로 확인한 뒤 단조 시계 주입 (§23)
- Python 50줄 **TCP 중계기**를 작성해 서버는 살린 채 앱만 끊는 실서버 검증 → 보관 메시지 4~8초 내 재전송 확인 (§23)
- 날씨 기능 시험 **45건(0.3초 미만)**. 한글 글꼴 때문에 CI에서 반드시 깨지는 골든 이미지 시험을 위젯 시험 5개로 교체해 이식성 확보 (§24.7, §25)

### 5. PoC 기반 기능 확장

- 재사용 캐시를 agent(LLM) 없이 검증하려고 계약만 흉내 내는 스텁(`fake_agent.py`)으로 전체 파이프라인을 태움 → `MISS`→`HIT` 확인 후 백그라운드 갱신 · 유한 큐(OOM 방지)로 확장 (§2)
- "지하철만 된다"는 말을 확인하러 갔다가 ODsay 대중교통 **9종** 연동 (§13)
- 동행자 위치 공유를 보류하고 일반 GPS + 폴리라인을 먼저 하도록 범위 축소를 팀 회의로 확정 (§7)

### 6. 칸반 기반 협업과 다중 저장소 통합

- FastAPI(hub) · Spring Boot(user) · Flutter(client) **3개 저장소 PR 3건**(hub #14 · client #77 · user #30) 전부 `develop` 머지. 충돌 직접 해소 후 develop 대비 **삭제 라인 0개** 검증 (§21)
- 묻지 않고 리베이스한 판단 착오를 발견하고 강제 푸시 없이 되돌림 — PR 닫기 → 로컬 복원 → **머지로 재해결**, 원래 커밋 SHA 6개 보존 (§24.8)
- `backlog / in-progress / done` 3단 보드와 개발 로그로 작업 상태 · 판단 근거 · 시행착오 기록
- 공유 개발 기계에서 다른 세션의 도커 스택을 건드리지 않도록 **격리 환경** 구성(DB · Redis 인덱스 · 컨슈머 그룹 · 포트 분리). 락 대신 격리를 고른 이유까지 문서화 (§24.5)

### 7. Spring Boot 백엔드 설계

- **인증 도메인 초기 구현** — JWT RS256, 카카오 OAuth, 리프레시 토큰 재사용 탐지, 레이트리밋, AES 컬럼 암호화 컨버터 (`fce2d8c`, 58파일 +3,696줄)
- **추천 재사용 캐시** — 요청 정규화 해시, 예산 내림 · 시간 반올림 매칭, Redis DB 용도 분리. 채팅 예약 DB5와의 충돌을 발견해 DB6으로 이동 (§1)
- **날씨 감시 배치** — 순수 함수 판정 규칙, 일정별 예외 격리, 멱등 마이그레이션(컬럼 7개 + 부분 인덱스), 의도적 무백필 (§24.1)

## 쓸 때 주의

- **채팅은 "구현했다"로 쓰지 않는다.** 3회 시도 중 2회는 팀 쪽이 먼저 머지해 폐기됐다. "장애를 재현 가능하게 만들고 결함 6건을 찾았다"가 사실이고, 실제 반영분은 PR #80 하나다.
- **"애자일"은 스크럼 의식(스프린트 · 회고) 근거가 없다.** 칸반 보드 · 짧은 PR 주기(PR #80은 브랜치 생성부터 머지까지 약 1시간) · 반복적 범위 조정은 근거가 있으므로 "칸반 기반 반복 개발"로 쓴다.
- **인증은 "초기 구현"으로 쓴다.** 18+ 정책 · 부팅 설정 검증 · state 검증은 팀원(류제무) 작업이다.
