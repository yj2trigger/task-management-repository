## 1-2. 나의 사고 과정 (유도 → 첫 반응 → 짚인 빈틈 → 바뀐 생각)

> 결과(AD)보다 **어떻게 생각이 움직였는지**가 면접에서 더 자주 묻힌다. 설계는 "답을 주지 않고 질문으로 유도"하는 방식으로 진행됐다(§4). 아래는 단계마다 어떤 질문을 받았고, 처음에 어떻게 답했고, 어디가 짚였고, 어떻게 고쳤는지다. 모든 인용은 세션 발화다.
> 맨 아래 표에 **내가 낸 것 / 위임한 것 / 처음에 틀렸다가 고친 것**을 따로 모았다. 면접에서는 이 셋을 구분해 말할 수 있어야 한다.

### 단계별 사고 흐름

**① 0단계 — 품질 속성 순위 (09:13)**
- 질문: 5개 속성(시연 안정성·구현 속도·성능·적응성·교체 용이성)을 1~5위로, 1·2위의 이유와 함께.
- 첫 답: "1 적응성, 2 구현 속도, 3 교체 용이성, 4 시연 안정성, 5 구현 속도", 팀원 2명. **이유는 적지 않았다.**
- 짚인 곳: ⓐ "구현 속도"가 두 번 들어가고 **"성능"이 빠짐**(앞서 "최적화가 매우 중요하다"고 한 말과 충돌 가능). ⓑ 이유가 없음. ⓒ 시연 안정성은 심사 ③ 문구 그대로인데 4위로 둠.
- 바뀐 생각: 순위 매기기에서 **"선을 문장으로 정의"**로 이동. 구현 속도는 "3일 이내, 기능은 포기하지 않고 설계로 맞춘다, 설계 기간은 3일에 안 들어간다", 교체 용이성은 "Croche가 예상과 달라도 대체·구조 변경 가능", 시연 안정성은 **"적응은 구조적으로 에러를 못 일으키되 바꿀 수 있는 도메인은 넓게"**, 성능은 "최대 시점 CPU 10%·1GB". 시연 안정성을 순위 항목에서 **제약으로 옮겨 놓은** 것이 이때의 핵심 전환.
- 사실 기록: 🤖의 질문은 셋(제약 고르기 / 남은 목표 순위와 이유를 심사 기준 번호로 / 시연에서 적응 보이기)이었다. 답은 "1. 시연 방안, 2. 제약 정리, 3. 위에서 충분히 설명했습니다" 순서였고 **적응성 줄은 비어 있었다.** 목표 1위의 이유는 다음 답(09:57)에서 "대화 적응이 가장 중요하고, 대화 외 요소도 빈도·시점·내용에 영향"이라고 말로 적었다. 심사 ②·④ 번호를 붙인 근거는 🤖가 §8-1에 채운 것이다.

**② 적응을 시연에서 어떻게 보이나 (09:35, 🙋가 직접 낸 방안)**
- 유도 질문: "며칠 써야 드러나는 성질을 몇 분 안에 보여 주는 방법을 한 문장으로."
- 🙋 내놓은 방안 3개: 데모 때 옆에 모니터링 화면 / 시간 빨리 감기 / Croche Studio의 AI 가상 사용자로 쌍을 이루어 같은 조작·다른 조작 비교("완전히 같지는 않고 경향만 같아도, 일장일단이 있을 것").
- 짚인 곳: 가상 사용자는 **대화**만 흉내 내는데 우리 적응 신호는 드래그·무응답·입력 강도 같은 비대화 신호가 많음 → **외부에서 신호를 주입하는 입구**가 구조에 필요. 차이의 원인을 셋(앱의 랜덤·앱의 규칙·Croche 문장)으로 나누면 앞의 둘은 통제 가능.
- 바뀐 생각: "경향만 같고 완전히 같지는 않다"고 본 **직관이 맞았고**, 원인을 분해하자 "판단은 앱이 하므로 행동 수준 재현성은 공짜"라는 결론이 나옴. 이후 가짜 관찰기(AD-34)·공통 시계(AD-26)·스냅숏(AD-30)으로 구체화.

**③ "백엔드"라는 말 (09:57)**
- 질문: "적응을 구현하려면 결국 백엔드가 필요하다"는 전제 — **서버인가, 앱 안의 데이터 처리 층인가?**
- 답: "앱 안의 데이터 처리층." (단어가 가리키는 대상을 분명히 함)
- 같은 답에서 🙋가 **스스로 "마감 전에 테스트해서 확인합니다"**(창 정보 읽기·클릭 통과)라고 정함 → 나중에 보니 이 한 문장이 AD-13이 되었고, A·B 결정의 위험을 낮춘 근거가 됨(§5-2 "실험이 비싼 결정을 싼 결정으로").
- 같은 답에서 **대화 적응이 가장 중요**하고 대화 외 요소가 대화의 **빈도·시점·내용**에 영향을 줘야 한다고 우선순위를 못박음 → AD-03(공통 상태 모델)의 출발점.

**④ 성능 수치 (09:57 → 10:05)**
- 첫 제안: "평상시 4%면 괜찮을까요?"
- 짚인 곳: PC 전체 기준 4%는 하루 종일 켜 두는 앱에서 체감됨, 평균이 최대치보다 중요.
- 바뀐 생각: **목표 2% / 상한 4%**로 수용. 이때 "평균 vs 최대"를 구분하는 사고가 들어옴.

**⑤ 결정 고르기 — 위임 (10:05)**
- 질문: 8개 결정에 의존 범위·발견 시점을 매겨 합이 큰 3개 고르기(G는 시범 풀이).
- 반응: "4. 잘 모르겠네요" → "어떤 느낌인지 알겠어요. **시간이 없으니까 일단 당신이 채우고 풀이해 주세요.**"
- **면접 주의:** 이 표는 🤖가 채웠다. 본인이 한 것은 방법을 이해하고 결과를 수용한 것. 방법(의존×발견, 실험이 위험을 낮춤)은 설명할 수 있어야 한다.

**⑥ 서버 확장 요구 (10:05)**
- 첫 생각: 먹이 데이터가 많아져 "로컬만으로는 감당이 힘들 수도" → 외부 서버를 두고 확장 용이하게.
- 짚인 곳: 느낌을 숫자로 바꿔 보니 용량은 이유가 못 됨(경로만 저장 / 1,000개도 1GB 미만). 서버가 필요한 진짜 이유는 동기화·B2B·백업·대량 임베딩.
- 바뀐 생각: **"지금 만들지 않되 문은 열어 둔다"**(저장소 인터페이스). 요구("확장 용이")는 버리지 않고 방식만 바뀜 → AD-01.

**⑦ 결정 E — 직관을 구조로 (10:13)**
- 질문: 해석 상태 5~8개와 올리고 내리는 신호를 적어 보라(한두 개는 직접).
- 🙋 응답: 해석 상태 목록을 적는 대신 **구조에 대한 아이디어 3개**: 상황별 성향 분리, 눈치 보는 고양이는 가중치를 전반적으로 높게, 텍스트로 적응하는 방법.
- 짚인 곳과 바뀐 점:
  - 상황별 분리 → 데이터가 쪼개져 새 앱은 기록 0건 → **계층 + 위층 빌려 쓰기**로 보완.
  - 눈치 고양이 → 🤖가 "가장 좋다"고 평가. **k값 = 고양이 성격**으로 번역되어 "고양이마다 다르게 배움"(차별성)으로 연결.
  - 텍스트 적응 → 표류·비용·재현성·모니터링 불가 → **판단은 숫자, 표현은 칸이 정해진 텍스트**로 절충.
- 이 단계에서 사고의 특징: 질문한 항목(상태 목록)에 직접 답하기보다 **더 위 수준의 구조 아이디어**를 먼저 냄. 그 아이디어들은 대부분 살아남았고(AD-05·06), 함정만 보완됨.

**⑧ Croche 선택지 — 확장과 한계 (10:21 ~ 10:36)**
1. 🙋 제안: 행동·말을 Croche에게 **선택지 형태**로 → 저녁 + 하루 마감 패턴이면 "하루가 어땠는지" 묻기.
2. 충돌 발견: "판단은 우리 앱" 원칙과 부딪힘 → **두 층**(0층 앱 혼자, 1층 앱이 시점·메뉴, Croche가 선택)으로 경계 재설정. 🙋 동의.
3. 🙋 확장: "AI가 **대화나 사용자 행동을 반영해 새로운 선택지를 추가해 가며 확률도 바꿔 가게**."
4. 🤖 안전장치: 새 조합만, 새 부품은 불가, 시험→정착→퇴출.
5. 🙋 정정: "확률보다는 **식이나 가중치**가 맞는 표현."
6. 🤖가 식을 데이터로 표현해 AI가 식의 모양까지 바꾸는 안 제시.
7. 🙋 **철회: "식을 수정하는 건 위험해 보이네요."** → 식은 고정, 가중치만 변경(AD-09).
- 사고의 특징: **확장 요구를 계속 키우다가, 위험이 보이는 지점에서 스스로 선을 그음.** 적응 범위를 넓히라는 요구(제약 "바꿀 수 있는 도메인은 넓게")와 "에러를 못 일으킨다"는 제약을 동시에 지키는 선이 "값은 바꾸되 코드 경로는 안 바꾼다"였다.
- 시연 선택(Croche 선택을 그대로 둘지, 기록 재생할지)은 **"(가) 그대로 둔다"**를 골랐다. 근거는 메뉴 항목이 모두 정상 행동이라 어느 것을 골라도 시연이 성립하기 때문.

## 14. 면접에서 쓸 수 있는 소재 (기록된 근거만)

| 예상 질문 | 답의 뼈대 | 근거 위치 |
|---|---|---|
| 왜 Croche에 모든 판단을 맡기지 않았나? | 성능·비용(몇 초마다 LLM 호출 불가), 반응 속도(드래그 반응을 2초 기다릴 수 없음), **대화 빈도·시점이 적응의 결과라 흔들리면 안 됨.** 그래서 0층/1층 분리 | §5-5, AD-07 |
| Croche가 이상한 걸 고르면? | 메뉴 밖 선택은 버리고 점수 1등 실행. 메뉴의 모든 항목이 이미 검증된 정상 행동이라 에러가 구조적으로 불가능. "말 안 걸기"도 늘 포함 | AD-02·07·08 |
| 적응이 에러를 일으키지 않는다는 걸 어떻게 보장? | "적응은 값만 바꾼다." 모든 값에 스키마·범위·기본값(카탈로그), 하루 변경 한도, 새 선택지는 새 조합만 허용. 식을 AI가 바꾸는 안은 **본인이 위험하다고 판단해 버림** | AD-02·08·09, §5-6 |
| 서버가 필요 없나? | 용량은 이유가 못 됨(경로만 저장, 1,000개도 1GB 미만). 동기화·B2B·백업은 해커톤 이후. 인터페이스로 문만 열어 둠 | AD-01, §5-3 |
| 적응을 3일 시연에서 어떻게 보이나? | ① 적응 대시보드(변경 기록이 곧 화면) ② 시연 전 스냅숏 불러와 모든 심사위원이 같은 출발점 ③ 공통 시계로 빨리 감기 ④ 가짜 관찰기/가상 사용자로 신호 주입. 행동 수준은 시드 고정 시 재현됨 | §4-2, AD-14·26·30·34 |
| 저장을 왜 세 곳으로? 비효율 아닌가? | 저장 공간은 불리하다고 **인정**하고 선택. 하루 5,000건×100B≈0.5MB라 감당 가능. 성능(정책은 캐시만 읽음)과 모니터링(변경 기록=대시보드 데이터)·재현에서 이득 | AD-14, §6-1 |
| 눈치 보는 고양이는 뭔가? | 상황 계층 성향 식의 k를 성격 값으로. 눈치 많은 고양이는 다른 상황 기록도 크게 반영. 같은 사용자라도 고양이마다 다르게 배움(차별성) | AD-05, §5-4 |
| 왜 해석 상태는 메모리, 성향은 DB? | 바뀌는 속도가 다름. 해석 상태를 DB에 쓰면 변경 기록이 하루 수만 줄 쌓여 잡음·성능 문제. 성향은 검증·기록 기능이 필요. 캐릭터가 살아 있는 것처럼 즉각 반응해야 함 | AD-17, §7-2 |
| 구성요소는 어떤 기준으로 나눴나? | ① 바뀌는 이유가 같은 것끼리 ② 데이터마다 고치는 쪽 하나 ③ 속도가 다른 일은 섞지 않음. 화살표를 그려 보니 행동 결정기에 7개가 몰려 셋으로 쪼갬 | AD-16~18, §7 |
| 시나리오 추적에서 뭘 발견했나? | "피곤해"가 Croche 기억에 영구 저장되는 문제(AD-22), 기분 나쁜 날의 답을 소재 반응이 나쁜 것으로 오학습하는 문제(AD-23). 구조도로는 안 보이고 장면을 따라가야 드러남 | §8 |
| 어느 앱에서든 걷는 건 어떻게? | 직접 측정: 화면 이미지 경계 추출이 20~26ms로 싸고 앱과 무관하게 상자 윗변을 오탐 없이 찾음 → 주력으로 승격. 접근성 정보(532ms, 앱마다 품질 다름)는 의미 보강으로 강등 | AD-25, §9-1 |
| Croche가 끊기면? | 어떤 실패도 고양이를 멈추게 하지 않음: 템플릿 모드, 회로 차단기, 하루 호출 상한. 사용자에겐 "졸린 고양이"로 보이게 숨기고, 장애는 대시보드·발표에서만 | AD-27·32, §10 |
| 장애를 왜 숨겼나? 심사 ④와 충돌하지 않나? | 목표는 애완동물처럼 보이는 것이라 오류 표시는 "프로그램"처럼 보이게 한다고 본인이 판단. 심사 ④는 대시보드 건강 상태 패널과 발표로 대응 | AD-31·32, §10-1 |
| 본인의 역할은? | 🅱 AI·데이터(Croche 연결, 메뉴·대화·먹이 창고·학습기·저장소·대시보드). 임계 경로(Day 1 Croche 연결)와 계약 K1~K6 초안 담당 | AD-33, §11 |
| 리스크는? | Croche SDK가 10/14에야 공개(어댑터·가짜 연결기로 대응), Electron 투명 창 성능 미측정, 창 정보 읽기·클릭 통과 미검증(AD-13) | §5-2, §10, §11 |
