이 조건이 계획에 미치는 영향:

- 보고서에 데이터 이름과 aihub.or.kr을 **반드시** 적는다. 이 과제의 정식 데이터명은 "수어 영상"과 "재난 안전 정보 전달을 위한 수어영상 데이터"이다.
- 원본뿐 아니라 **원본을 단순 가공한 것**(추출한 좌표 배열 등)도 외부에 공유할 수 없다고 읽힌다. 따라서 좌표 배열은 GitHub(비공개 레포 포함)에 올리지 않고 D 드라이브에만 둔다. 팀원 간 공유 방식은 "제3자"에 팀원이 해당하는지가 불분명하니, 각자 같은 코드로 직접 추출하는 쪽이 안전하다.
- 보고서 그림은 스켈레톤 이미지를 기본으로 하되, 필요하면 최소 범위의 원본 프레임 예시는 쓸 수 있다(앞서 "원본 프레임은 쓰지 않는다"고 한 것보다 완화됨). 다만 얼굴이 나오는 프레임이라는 점은 별도로 고려한다.
- 위 문구는 화면 캡처에서 옮긴 것이다. 보고서에 넣기 전 AI-Hub 원문과 대조한다.

## 판단 근거

- 1번 파일 두 개를 먼저 받아 구조를 확인한다. 이 결과로 2번(117GB)을 받을지 최종 결정한다. 117GB를 받은 뒤에 구조가 기대와 다르면 시간 손실이 크다.
- **(정정, T-002)** 위 판단 중 "Validation만으로 시작, 수행자 51명"은 틀렸다. Validation 단어 데이터의 수행자는 2명(REAL17, 18)뿐이다. 수행자 독립 분할을 하려면 Training(REAL01~16, 추정)의 영상이 필요하다. Training 단어 영상은 32개 파일(각 약 30GB, 파일 하나가 수행자 한 명의 단어 절반인 것으로 추정)이라 수행자를 몇 명 받을지 정해야 한다. 이 추정(파일↔수행자 대응)은 파일을 받아 보기 전에는 확인하지 못한다.
- Training 단어 영상은 모델 성능이 데이터 부족으로 막힐 때에만 일부 파일을 추가한다(그때 원인을 `trials.md`에 기록).

## 다운로드 방법 (2026-10-18 점검)

AI-Hub API 다운로드 스크립트(`aihubshell` v0.6, `https://api.aihub.or.kr/api/aihubshell.do`)를 받아 내용을 읽고 파일 트리 조회까지 해 봤다. 인증 키가 없어 실제 다운로드는 시도하지 못했다.

| 확인한 것 | 결과 |
|---|---|
| 서버 연결 | 가능(HTTP 200) |
| 데이터셋 번호 | 수어 영상 **103**, 재난 안전 정보 전달을 위한 수어영상 **636** |
| 파일 키 | 위 표의 키(39478, 39483, 39479, 62027 등)가 파일 트리에 그대로 있음 |
| 병합에 WSL 필요 여부 | 스크립트의 병합은 `find/sort/xargs cat`이라 Git Bash에서 실행 가능해 보임. 실제로는 아직 돌려 보지 않음 |

스크립트 동작(읽은 내용 기준): `curl -L -C - -H "apikey:<키>" https://api.aihub.or.kr/down/0.6/<데이터셋번호>.do?fileSn=<파일키>`로 현재 폴더에 `download.tar`를 받고, 풀고, `.part*` 파일을 병합한 뒤 조각과 tar를 지운다.

주의:
- 다운로드 시작 시 기존 `download.tar`가 있으면 이름을 바꿔 치우고 처음부터 다시 받는다. 즉 중간에 끊기면 **이어받기가 되지 않는다**. Ctrl+C 시에는 `download.tar`를 삭제한다. 117GB를 받을 때는 같은 주소로 `curl -C -`를 직접 호출해 이어받는 방식을 쓰는 편이 안전해 보이지만, 서버가 이어받기(Range)를 지원하는지는 확인하지 못했다.
- 인증 키는 환경변수 `AIHUB_APIKEY`로 읽는다. 키는 대화나 파일에 쓰지 않는다.
- 현재 폴더에 받으므로 반드시 D 드라이브에서 실행한다. 최대 용량은 tar + 풀린 조각 + 병합본으로 약 3배가 일시적으로 필요하다(117GB 파일이면 약 350GB).

## 103 Training 단어 영상 파일 대응표 (2026-10-19 확인, T-012)

각 파일의 앞 3MB만 받아 zip 첫 항목 이름을 읽어 확인했다(전체 다운로드 없이).

| 파일 번호 | 파일 키 | 수행자 | 단어 번호 | 폴더 이름 |
|---|---|---|---|---|
| 홀수 01, 03, …, 31 | 39546, 39548, …, 39576 (= 39546 + 2×(수행자−1)) | 수행자 1~16 | **1501~3000** | `NN` |
| 짝수 02, 04, …, 32 | 39547, 39549, …, 39577 | 같은 수행자 1~16 | 1~1500 | `NN-1` |

- 한 파일 = 수행자 1명 × 단어 반쪽(1,500단어 × 5시점 = 7,500개, 약 30GB, 그중 정면 1,500개).
- 선정 100단어(1501~3000번)는 홀수 파일에만 있다. 짝수 파일은 클래스를 1~1500번까지 넓힐 때만 필요하다.
- Validation(키 39483)은 수행자 17·18이 단어 1~3000 전부를 한 파일에 담고 있다(117.79GB).
- 받은 zip은 클래스를 확대할 때 재다운로드 없이 쓰도록 보관한다(필요한 100단어는 정면 영상 100개, 약 0.44GB뿐이라 낭비가 크지만 서버가 파일 단위로만 내려준다).

## 실행 방식 (확인 필요 항목 포함)

- 분할 압축 파일은 병합이 필요하다. 안내문은 리눅스 명령(`find … | sort | xargs cat`)과 WSL을 권하지만, 같은 일을 Python으로 조각 번호 순서대로 이어 붙이면 Windows에서도 된다. 이 방법이 실제로 동작하는지는 아직 확인하지 않았다.
- 병합하면 조각과 병합본이 동시에 있어 일시적으로 용량의 2배(약 236GB)가 필요하다. D 여유 안에서 가능하다.
- 병합본 전체를 풀지 않고 필요한 파일(정면 시점)만 `zipfile`로 골라 읽는 방안을 우선 시도한다.
- 정면 시점을 어떻게 구분하는지(파일명 규칙)는 압축 파일을 열어 본 뒤 확인한다. 지금은 알지 못한다.
