### 0.1 "user 레포가 빈 깡통" 주장 검증

**상황:** "user 레포가 깡통(껍데기)이다"라는 얘기를 들었다는 제보로 미구현 여부 확인 요청.

**조사:** java 파일 49개 중 `*Placeholder.java` 5개(auth/common/config/recommend/schedule)만 마커, 나머지 44개는 실 로직. recommend/schedule/trip 도메인은 다 구현 확인, 테스트는 스모크 1개뿐.

**결론:** "전체가 빈 깡통"은 과장. auth 도메인만 실제로 미착수(`AuthPlaceholder.java` 하나뿐)였던 시점.

### 0.2 인증 도메인 실제 위치 확인 — 당시 PR#7 아님

**상황:** 인증이 PR#7이 아니라 다른 브랜치에 있다는 제보.

**조사(당시 기준):** PR#7(`feat/auth-domain-init`)은 CLOSED. `origin/feat/login-dev`가 실제 작업 브랜치였고, 그 시점엔 PR 자체가 미생성 상태였음(현재는 PR #21로 오픈됨 — §8 참고).

**발견:** `feat/login-dev`의 V004 마이그레이션이 `trips`/`trip_recommendations`/`trip_segments` 명명을 썼는데, SSOT(요구사항/아키텍처 v5.0)는 `trips` 명명을 명시적으로 폐기 처리해둔 상태라 충돌 확인.

→ 동일 발견이 `CURRENT_STATE.md` "인증 도메인 현황" 절에 더 자세히 정리돼있음(중복 아님,
그쪽이 정본).

### 0.3 기능정의서 대조 gap 분석

**상황:** 기능정의서 기준 map-service-user 관련 17개 요구사항 구현 여부 검사 요청.

**결론(당시 기준):** 일정 CRUD는 생성만 존재, 재탐색 3모드/재사용 정책(`(schedule_id, stage)` lookup, `X-Force-Refresh`)/Redis DB 용도분리/`user_service` 20테이블 등 대부분 미구현 확인.

→ 이 gap 분석이 `tasks/map-verification-plan.md`의 V-B~V-L 체크리스트 전체로 발전함 —
항목별 세부 확인 상태는 그 문서 기준.

### 0.4 jobId vs schedule_id 시점 문제 발견

**상황:** 재사용캐시의 키를 `(schedule_id, stage)`로 할지 jobId로 할지 논의.

**조사:** `ScheduleService.persist()`는 클라이언트가 "저장" 확정한 시점에만 실행 — `schedule_id`가 이 시점에야 발급됨. 재탐색(저장 전 단계)엔 아직 schedule_id가 없어 lookup 키로 못 씀. jobId는 매 생성 호출마다 새로 발급돼 "이전 요청 재사용" 키로도 부적합.

**판단:** SSOT 아키텍처 v5.0 §7.1 재확인(poppler 없어 `pdftotext`로 우회) 결과, 원래 의도된 흐름은 "`POST /schedules` 먼저 → scheduleId 발급 → 그 다음 agent 호출 → `schedule_recommendations(stage=1)`에 누적"이었음 — 즉 schedule-first 구조가 SSOT 의도였고, 당시 develop 구현(agent 먼저, 저장은 최후)이 이와 어긋나 있었음. 다른 팀원 작성 코드라 이 발견만으로 임의 수정하지 않기로 결정.

→ 이 발견이 곧 `tasks/map-verification-plan.md`의 **PRE-05**, `CURRENT_STATE.md`의 "SSOT
재정합 필요 항목" 절로 정식 등재됨 — 상태는 여전히 "미해소, 팀 논의 필요"로 두 문서와 일치
확인함(2026-07-27). "poppler 없어 pdftotext로 우회"한 조사 방법 자체는 그 두 문서엔 없는
이 로그만의 디테일.

### 0.5 스코프 확정 — PoC 지나 전체 기능 구현, 사용자간 캐시로 확정

**판단:** "PoC 단계는 지나서 모든 기능을 구현해야 한다"고 스코프 확정. 문제를 두 갈래로 분리:
- **중복호출 dedup**(같은 액션 재시도 방지) — 클라이언트 발급 Idempotency Key로 해결, auth 불필요
- **조건매칭 재사용**(사용자간 캐시, "장소 N개 캐시+나머지 신규") — 원래 운영단계 기능, 스코프 확정으로 구현 대상. **"사용자간"으로 확정하면서 user_id 스코핑 자체가 불필요해짐** — auth(`feat/login-dev`) 병합 여부와 무관하게 진행 가능해진 게 이 시점의 핵심 결론.

**리서치:** Idempotency Key 표준 패턴(클라이언트 발급 키 + Redis + 동시요청 lock) 확인. `spring-idempotency-kit` 라이브러리 후보로 검토(기존 `RedisConfig` 멀티DB 패턴과 호환).

→ 이 스코프 결정이 `CURRENT_STATE.md`의 "진행 중 — 추천 재사용/Idempotency 설계" 절과
동일 내용. "사용자간 캐시로 확정, user_id 스코핑 불필요"라는 이 시점의 결론은 실제 구현된
`RecommendCacheKey`(§1 이후 커밋)가 province/city/theme/mobility/budget/date만으로
해시를 만들고 user_id를 아예 안 쓰는 것과 정확히 일치함(2026-07-27 코드 대조 확인) —
결론이 그대로 구현까지 이어졌음.

### 0.6 client 실제 연동 확인 — `/api/v1/trip/generate` 위험 발견

**조사:** `map-service-client`의 `trip_api_service.dart`가 `/api/v1/recommend` 비동기 API를 안 쓰고 `/api/v1/trip/generate`(동기 facade)만 호출, 타임아웃 설정 없음을 확인.

**원인 분석:** `TripService.awaitDraft()`가 서버 스레드를 최대 120초 폴링 블로킹. 배포 시 AWS ALB 기본 idle timeout(60초) < 120초라 ALB가 먼저 연결을 끊을 수 있음 — HTTP 응답은 원 연결로만 돌아오므로 끊긴 연결의 응답은 재전송 응답과 경쟁하는 게 아니라 아예 도달 통로가 사라져 유실됨. 재전송(새 연결)만 도착 — agent 호출은 이중으로 나가고 첫 결과는 순수 낭비.

**결론:** 재사용/idempotency 설계는 `/api/v1/recommend`보다 `/api/v1/trip/generate`를 우선 대상으로 삼아야 한다고 정리. 이후 §1부터 실제 구현 커밋 시작.

→ `CURRENT_STATE.md`의 "trip 도메인 현황"/"알려진 버그 #4", `map-verification-plan.md`
V-F 절의 "추가 발견" 문단과 동일 내용 — 세 곳 다 일치, 이 결론 이후로 갱신된 바 없음
(2026-07-27 확인).

## 5. "동행자 위치 공유" 후보 등장 → 설계 전제 재검토 (2026-07-22)

**상황:** GPS-02 활용처 후보로 "동행자 위치 공유"(여행 중 동행자끼리 서로 위치 확인)가
유력하게 떠오름. 기존에 세워둔 "본인 기기 위치만 다루면 됨 → pub/sub 불필요" 전제와
정면으로 부딪힘(동행자가 내 위치를 실시간으로 봐야 하니 다중 구독자 시나리오가 됨).

**판단:** 그래도 그룹 규모가 4인 안팎으로 작아서, WebSocket/MQTT 같은 push 인프라 없이
짧은 주기 폴링(REST)만으로 충분하다고 판단. 이 프로젝트가 이미 쓰는 job polling 패턴과
동일 방식이라 재사용 가능.

**결론:** "로직 합의" 확정 — 위치 → 서버 저장 → 동행자가 일정 주기(예 5초)마다 조회.
실시간 웹소켓/MQTT는 로드맵에서 명시적으로 제외.

## 7. 범위 축소 — 동행자 공유 보류, 일반 GPS + 폴리라인 먼저 (2026-07-24)

**상황:** 동행자 위치 공유(실시간 조회/공유중단 등)까지 미리 코드로 만들어두면, 나중에
그 기능을 실제로 켤 때 팀원들이 "이미 있던 코드인데 왜 반쯤만 동작하냐"며 헷갈릴 수 있다는
우려가 나옴.

**판단:** 동행자 공유는 의도적으로 나중에 한 번에 구현하기로 미루고, 지금은 여행 종료 후
이동 경로(폴리라인)를 지도에 그려 재생하는 "일반 GPS ping 수신 + 영구 저장"만 먼저 만들기로 함.

**결론:** 이미 만들어뒀던 Redis 기반 `LocationStore`(TTL 20초, 동행자 실시간 조회용)를
삭제. 대신 Postgres 영구 저장(`location_logs` 테이블, append-only)으로 설계를 갈아엎음 —
Redis는 이번 범위에서 아예 안 씀.

## 13. ODsay 대중교통 연동 — "지하철만 된다"는 말을 확인하러 갔다가 9종을 붙임 (2026-07-28~08-11)

제일 나쁘다고 봤기 때문이다.

범위부터 재보기로 한 것이 결과적으로 맞았다. 확인해보니 기존 구현은 정말로 지하철

   스키마를 먼저 박으면 나중에 계약을 두 번 깨야 한다.
2. **지도 좌표를 `loadLane`으로 못 얻어 우회함** — ODsay `loadLane`이 실호출에서 계속

## 15. 통합 길찾기 경로 후보 + 경유 정류장 목록 (2026-08-12~13)

> 대상 저장소: `map-service-hub` → `map-service-user` → `map-service-client` 3단
> 커밋: hub `ebe9b52`·`59ca7f3` / user `5955837`·`ace3bc1` / client `ac6a274`·`8732645`

**상황:** 목표는 화면 단위로 정해져 있었다(2026-08-12 17:02) — 두 지점 사이 **가능한
이동 방법을 목록으로 나열**하고, 하나 고르면 **지도 위에 그 경로를 표시**. 디자인은 앱의
다른 화면들을 그대로 따를 것. 이어서(20:50) *"N개 정류장"* 표시를 누르면 **실제 지나는
정류장 이름들**이 보이게 하는 요구가 추가됐다.

**판단:**

- **기존 지하철 전용 경로를 고치지 않고 나란히 두기로 함.** `/v1/transit/subway`는
  그대로 두고 `pathType` 필터 없는 `/v1/transit/routes`를 따로 냈다. 남의 작업을
  건드리지 않으면서 기능을 늘리는 쪽을 택한 것.
- **재사용할 것은 재사용했다** — 지하철 전용 조회의 스텁/캐시/일일호출한도/예비키 재시도
  로직을 그대로 쓰고 **캐시 키 네임스페이스만 분리**했다.
- **user(BFF)는 위임만 한다** — 기존 `SubwayRouteController/Client`와 **같은 패턴**으로
  `TransitRouteController/Client`를 만들어 hub를 부른다. 새 패턴을 만들면 다음 사람이
  둘 중 뭘 따라야 할지 모른다.
- **`stops`에서 geometry와 다르게 처리한 지점** — 둘 다 같은 `passStopList.stations`
  원본에서 뽑지만, **좌표(geometry)는 없을 때 시작/끝으로 대체**하고 **이름(stops)은
  대체하지 않고 빈 리스트로 둔다**. 이유: "몇 개를 지나는지" 목록에 시작/끝만 지어내
  채우면 **실제 경유 수를 오인시킨다**. 지도에 선이 안 그려지는 것보다 개수를 속이는
  쪽이 나쁘다고 판단.

**결론:** 3단 전부 연결됨.

- hub `/v1/transit/routes` — 소요시간 순 **최대 8건**, 각 구간에 지도용 `geometry` 좌표열
  포함(프론트가 이동수단별로 색 구분 가능). 이후 `stops` 필드 추가.
- user — hub 5xx를 `TransitRouteException`으로 변환해 **502**로 응답하도록 전역 예외
  핸들러에 매핑 추가. `stops`는 그대로 전달.
- client — 경로 목록/지도 화면 추가, "N개 정류장" 탭 시 경유 정류장 목록 표시.

**검증 상태:** 폰 확인은 완주하지 못했다 — 2026-08-13 04:17 시점에 **로그인 단계에서
막혀** 정류장 chip 기능까지 도달하지 못했고, 날씨 기능도 더미 API 키 때문에 안 떴다.
홈 화면 외형만 확인된 상태. **실기 기능 검증은 미완으로 남아있다.**

## 17. 지하철 버튼에서 "사실상 버스" 경로 걸러내기 — 임계값을 실측으로 정함

> 대상 저장소: `map-service-hub` → `map-service-user` → `map-service-client` 3단
> 커밋: hub `a545346`·`32d08f0` / user `3e8cb4d` / client `b14afba`

**상황:** §15로 통합 길찾기 목록은 됐는데, 지하철 버튼을 눌러도 실제로는 "버스 30분 +
지하철 두 정거장 + 버스 20분" 같은, 사실상 버스로 가는 경로가 섞여 나왔다. *"지하철
버튼을 누르면 보통 버스-지하철-버스 순으로 이용하게 되잖아요? 버스로 이동하는 거리와
지하철로 이동하는 거리를 받아와서 버스가 90% 이상이면 배제하는 느낌으로 가능한가요?"*
로 요구가 왔다.

**판단:**

- **숫자를 감으로 정하지 않았다.** 90%를 그대로 쓰기 전에 *"80% 지웠을 때 유일한
  경로가 지워진다거나 등등의 문제가 없는지 찾아보세요"*라는 지시로, 수도권뿐 아니라
  속초·강릉·전주 등 **지방 11곳을 포함한 24개 구간·257건의 실제 ODsay 응답**을 재서
  임계값을 골랐다. 결과 **0.80**으로 확정 — 이 선에 걸리는 건 257건 중 4건뿐이고
  전부 "지하철 2km 이하 + 버스 10km 이상" 형태였다. 0.70으로 내리면 지하철을 13km
  넘게 타는 정상 경로까지 걸렸다.
- **거리 필터(subway·bus만, 도보 제외)로 갔다.** 시간으로 재면 "버스를 오래 탔다"와
  "버스가 막혔다"가 구분되지 않는다. 같은 거리라도 버스는 신호·정차로 시간이 늘어나기
  때문이다.
- **필터가 후보를 전부 지우면 적용하지 않는다.** 지하철이 들어간 길이 분명히 있는데
  화면에 "없다"고 내보내는 것이 지하철 아예 없는 지역과 뒤섞이는 것보다 나쁘다고 봤다.
- **원격 카테고리 분류부터 확인 후 결정했다.** *"원격 레포에 카테고리 분류 뭐로
  되있는지 확인하세요. 지하철, 버스만 있는지 아니면 지하철, 버스, 혼합으로 있는지
  보고 결정할게요"* — 혼합 카테고리가 없는 걸 확인한 뒤 "버스는 버스만 있는 경로만,
  지하철은 80% 이상 버스인 것만 거른다"로 최종 방향을 확정했다.
- **필터는 hub 하나에만 둔다.** BFF·앱은 `mode` 값을 그대로 전달·통과만 시킨다
  (§16 이후 반복되는 원칙 — 규칙이 두 곳에 흩어지면 한쪽만 고치는 일이 생긴다).

**결론:** `GET /v1/transit/routes?mode=all|subway|bus`. `subway_distance_m`·
`bus_distance_m`·`bus_distance_ratio`를 후보마다 실어 보내 화면이 재계산하지 않고
그대로 쓸 수 있게 했다.

> **캐시가 새 필드를 몰라서 500** — 배포 직후 거리 필드를 추가했는데 예전 캐시 값엔
> 그 필드가 없어 `KeyError`로 죽었다. 폰으로 실제 조회해보다가 발견한 버그로, 단위
> 테스트로는 못 잡는 종류였다. 캐시 키 네임스페이스에 `v2`를 붙이고 필터 함수도
> `.get(key, default)`로 결측에 견고하게 고쳤다(`32d08f0`).

## 18. 도시 간 이동이 "도보 N분"으로 표시되는 버그 — 세 번 반복해서 깨달은 패턴

> 대상 저장소: `map-service-hub` → `map-service-client`
> 커밋: hub `b8d62fc`·`d051e57`·`075c327` / client `6e4b244`

**상황:** 안산 → 속초(234km) 실기 테스트 중 "도보 217분"이 나왔다. ODsay가 구간마다
주는 `trafficType`을 hub가 지하철(1)·시내버스(2) 둘만 알고, 나머지는 전부 걷는 구간으로
보고 있었던 것이 원인이었다.

**판단 — 여기서 반복된 패턴이 있다.** 문제를 하나 고치고 나면 "같은 원인의 다른 값"이
또 나왔다:

1. **1차: 시외버스(`trafficType=6`)** 를 고치고 "이제 됐다"고 보려 했는데, 그 전에
   *"기차 자전거 킥보드 시외버스 항공 다 뜨는지도 확인하세요. 실제로 작동하는지
   눈으로 봐야 믿을 수 있어요"*라는 지시로 범위를 넓혀 확인했다. 실측 결과 서울→부산
   19건 중 **열차 10건·고속버스 4건·항공 1건**이 섞여 있었다 — 시외버스 하나만
   고쳐서는 정작 흔한 노선(서울↔부산)에서 같은 버그가 그대로 재현되는 상황이었다.
2. **2차: 고속버스(`trafficType=5`)** 추가. 시외버스와 합치지 않은 것은 터미널·요금
   체계가 서로 달라서다.
3. **3차: 열차(4)·항공(7)** 도 매핑은 하되, **거리 비중 어느 쪽에도 넣지 않고
   지하철·버스 버튼 양쪽에서 뺐다.** 버스로 세면 KTX가 "버스 경로"가 되고, 빼기만
   하면 분모가 0이라 "버스 비중 0%"(곧 §17의 지하철 위주 판정)로 잘못 읽히기 때문.

**여기서 발견한 두 번째 버그 — 자르는 순서.** 목록은 소요시간 상위 8건(`ROUTE_OPTIONS_MAX`)
으로 자르는데, 이 절단이 §17의 mode 필터보다 **먼저** 걸려 있었다. 서울→부산은 빠른
순으로 열차·항공이 앞 8칸을 채워, 실제로는 고속버스 4건·시외버스 4건이 있는데도 버스
버튼이 "갈 수 있는 경로가 없어요"였다. **거른 뒤에 자르도록 순서를 바꿨다** — 정규화
단계에서는 자르지 않고 라우터가 필터 다음에 상한을 건다.

**결론:** 이동수단은 `walk`·`subway`·`bus`·`express`·`intercity`(+ 화면엔 안 나가는
`train`·`air`) 일곱 종류. `distance_m`이 있는 값 중 매핑이 빠진 게 있으면 어디선가
"도보 N분"으로 새는 구조라는 걸 이번에 세 번 겪고서야 체감했다 — **`trafficType`을
새로 하나 매핑할 때마다 "이거 말고 또 없나"를 먼저 확인하는 편이 저렴하다.**

## 19. 폰이 로컬 도커가 아니라 죽은 배포 서버를 보고 있던 문제

**상황:** §17·18을 실기로 확인하려는데, 로그인은 되는데 저장한 일정(`sokcho-test` 등)이
안 보였다. 계정 문제로 의심하고 로그아웃/재로그인, 앱 데이터 초기화(`pm clear`)까지
했는데도 그대로였고, **nginx 프록시 로그에 앱의 요청 자체가 안 잡혔다** — 로컬 도커에는
아예 안 오고 있었다는 뜻.

**판단:** 원격 설정 파일(`app_config.json`, 원래 Cloudflare 터널 주소를 게시해 두는
용도 — `docs/release.md` 참고)을 직접 열어보니 죽은 터널 주소를 가리키고 있었다. 앱은
"빌드 주입값 > 원격 > 마지막 성공값 > 로컬 기본값" 순으로 서버 주소를 정하는데, 지금
폰에 깔린 APK는 `--dart-define=API_BASE_URL`을 안 준 **배포용 빌드**라 원격 설정을
그대로 따르고 있었다. 게다가 패키지명이 `com.example.map_service_client`가 아니라
`kr.mapservice.client`였다 — 예전 패키지는 이미 지워져 있었고, 실제 설치본은 배포
파이프라인(`docs/release.md`)이 만든 것이었다.

**결론:** `flutter build apk --debug --dart-define=API_BASE_URL=http://localhost:8090`
로 로컬 hub를 직접 가리키는 디버그 빌드를 새로 만들어 설치하니 정상 연결됐다.
**"폰에서 뭔가 안 보인다"가 항상 서버·계정 문제는 아니다** — 이번엔 그 앱이 애초에
우리가 띄운 서버를 보고 있지 않았던 것이 원인이었다. 캐시 무효화(`pm clear`,
uninstall/install)로는 못 잡는 종류의 문제였다.

## 20. `loadLane` 재조사 — "실호출 계속 실패"는 형식 문제였다

> §13에서 `loadLane`(ODsay 도로 지오메트리 API)이 "`-8 mapObject 형식이
> 잘못되었습니다`로 계속 실패해 문서/실제 API 버전 불일치로 추정"하고 우회했던 것을,
> §18 작업 중 시외버스 경로가 직선으로 표시되는 걸 보고 다시 파봤다.

**상황:** 지도에 그려지는 시외버스 경로가 출발-도착을 잇는 **직선**이었다. 원인은
`_step_geometry`가 `passStopList`(경유 정류장)이 없으면 시작·끝 두 점으로 대체하는
로직이었고, 시외버스·고속버스는 애초에 이 목록 자체가 안 오는 노선이라 항상 직선으로
떨어졌다.

**판단:** "안 되는 API"로 결론 내리기 전에 웹 검색으로 실제 요청 형식부터 다시
확인했다. ODsay 개발자 포럼·가이드 문서를 보니 `mapObject` 파라미터는
**`0:0@` 접두사 + `searchPubTransPathT` 응답의 `info.mapObj` 값**을 그대로 이어붙여야
했다. 실험 스크립트로 직접 대조하니:

| 형식 | 결과 |
|---|---|
| `mapObject=0:0@{mapObj}` | **성공** — 서울시청→여의도 lane 2개, 좌표 164점 |
| `mapObject={mapObj}` (접두사 없이) | `-8 mapObject 형식이 잘못되었습니다` (기존에 보던 그 에러) |

즉 **API가 문서와 다르게 동작한 게 아니라, 처음 구현 때 접두사를 빠뜨렸던 것**이었다.
넓혀서 확인하니 서울↔춘천(lane 5개, 좌표 1,166점)·안산↔수원(lane 2개, 좌표 340점)도
정상 동작 — 지금 쓰는 `passStopList` 기반 좌표보다 **20배 이상 촘촘한 실제 도로
지오메트리**를 얻을 수 있다는 뜻이다.

**단, 시외버스·고속버스는 여전히 안 된다.** 그 두 종류는 `info.mapObj` 자체가 `None`으로
온다 — ODsay가 도시 간 버스 노선의 지오메트리를 아예 제공하지 않는 것으로 보인다.
`loadLane`을 도입해도 지하철·시내버스 구간의 곡선은 좋아지지만, §18에서 고친 시외버스·
고속버스 직선 문제는 **별도로(OSRM 등 도로 라우팅) 풀어야 한다.**

**결론:** 이번 세션엔 도입하지 않고 조사만 마쳤다(`b`·`c` 단계, 후속 작업으로 남김).
PR(hub #14 · client #77 · user #30) 본문에 "알려진 제한"으로 남겨 뒀다.

> **교훈 — "이전에 안 됐다"를 그대로 믿지 않기.** §13 시점의 판단(구현 대안으로
> 우회)은 그 자체로 합리적이었다("문서 문제로 추정"까지만 하고 대안으로 넘어감).
> 다만 그 추정을 나중에 실제로 검증해보니 우리 쪽 파라미터 조합 실수였다 — 과거
> 판단을 존중하되, 다시 볼 계기가 생기면 재확인하는 게 싸게 먹혔다.

### 22.2 웹소켓의 어려운 쪽은 연결이 아니라 끊김

연결 성립은 실서버로 한 번 확인하면 끝이지만, 끊김·거절·프레임 조각화는 **진짜 서버로는
원하는 순간에 만들 수 없다.** 그래서 서비스가 소켓을 직접 만들지 않고 통로
(`StreamChannel`)를 주입받게 열고, 가짜 통로로 장애를 직접 만들어 넣었다.
재연결 대기가 최대 30초라 `fake_async`로 시계를 앞당겨 **전체 시험이 0.1초에 끝난다.**

이 과정에서 구현 자체의 결함 4가지를 찾아 고쳤다.

| 결함 | 증상 | 조치 |
|---|---|---|
| 재연결 중 유실 | 끊긴 30초 동안 온 말이 영영 안 옴 (터널 하나면 재현) | 재연결 시 마지막 seq 이후를 다시 받아 병합 |
| 끊긴 동안 전송 | 조용히 버려짐. 사용자는 보냈다고 믿음 | 큐에 쌓았다가 재연결 시 발송 |
| 좀비 연결 | 하트비트를 보내기만 하고 수신 감시 없음 | 서버가 알린 주기 기준 3주기 무응답 시 재연결 |
| 재연결 몰림 | 서버 회복 순간 모든 기기가 동시에 재시도 | 대기에 30% 이내 흔들림 |

**시험이 아니었으면 못 찾았을 버그 2건:**

- `_teardown()`이 `sub.cancel()`과 `sink.close()`를 `await` 하고 있었다. 상대가 닫힘을
  확인해 주지 않으면 그 자리에서 돌아오지 않고, 이를 기다리는 `connect()`까지 멈춘다 —
  **방 전환 자체가 불가능해진다.** 시험이 계속 "연결 시도 1회"로 실패해 파고들다 찾았다.
- 좀비 감지를 `DateTime.now()` 차이로 판정하고 있었다. `fake_async`는 벽시계를 속이지
  못해 **시험 자체가 불가능**했고, 실사용에서도 절전 복귀·시계 동기화로 시각이 점프하면
  멀쩡한 연결을 끊는다. 틱 카운트 방식으로 바꿔 둘 다 해결.

### 22.3 계층 사이의 틈으로 빠진 버그

실시간 계층에 큐를 만들어 두고도 **실기 시연에서 메시지가 유실됐다.** 원인은 화면
계층이었다:

```dart
if (realtime != null && realtime.isConnected) { realtime.send(...); return; }
await _chatRepository.sendMessage(roomId, text);   // ← 끊기면 이쪽으로 샘
```

소켓이 끊겨 있으면 REST로 갈아탔는데, **소켓이 끊기는 상황은 대개 망이 나쁜 상황이라
REST도 함께 실패한다.** 그러면 큐에 쌓일 기회도 없이 사라진다. 서비스 단위 시험은 그
층만 봐서 전부 통과했다. 화면 계층 시험 5건을 추가해 고정했다.

> **교훈 — 계층별로 나눠 시험하면 계층 *사이*가 빈다.** 각 층은 자기 몫을 다 했는데
> 조합에서 새는 경우가 있다. 실기 시연이 그 틈을 드러냈다.

### 22.4 실서버 검증

가짜 통로 시험은 "우리가 정한 전제" 안에서만 참이다. 특히 좀비 감지는 *"서버가 하트비트를
보낸다"* 는 전제 위에 서 있는데, 그 전제가 틀리면 **조용한 방에 앉아 있기만 해도 주기적으로
끊겼다 붙기를 반복한다.** 가짜 통로로는 절대 드러나지 않는다.

그래서 실서버(PostgreSQL + Redis + Spring)를 띄우고 붙였다. 연결이 끊긴 상황을 만들려면
서버를 죽여야 하는데 그러면 "끊긴 사이 상대가 보낸 말"을 만들 수 없어, **TCP 중계기를
Python 50줄로 짜서 앱만 끊었다**(앱 → 8099 중계기 → 8081 서버).

| 확인 항목 | 결과 |
|---|---|
| 소켓 왕복 (전송 → 방송 → DB 저장) | seq 2 저장 확인 |
| `client_msg_id` 에코 | 일치 |
| 40초 무통신 연결 유지 | 유지 — 좀비 감지 오작동 없음 |
| 끊긴 동안 전송 → 서버 미도달 | 서버 최신 seq 고정(20) 확인 |
| 복구 후 큐 자동 발송 | **4~8초 내** seq 21 도착 |
| 끊긴 사이 상대 메시지 수신 | 재연결 후 화면에 채워짐 |

### 25.1 성능 지표 측정 방법과 원리

정성적 서술 대신 재현 가능한 두 지표를 실측했다.

**감시 쿼리(부분 인덱스) — 41배**
`idx_schedules_weather_watch`가 없을 때와 있을 때를 같은 데이터셋(PostgreSQL, 10만 건)에서
비교했다. 실제 서비스 분포를 가정한다 — 저장 일정 대부분은 이미 종료됐고(감시 대상 아님),
지역·기준선을 가진 것은 이 기능 이후 저장분뿐이다. 감시 대상을 100,000건 중 250건(0.25%)
으로 두고 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`을 각 7회 실행해 중앙값을 썼다.

| | 인덱스 없음 | 부분 인덱스 |
|---|---|---|
| 실행 시간(중앙값) | 16.0ms | 0.39ms |
| 읽은 버퍼 블록 | 9,742 | 252 |
| 접근 방식 | Seq Scan | Bitmap Heap Scan |

**왜 이만큼 차이 나는가.** 인덱스가 없으면 옵티마이저는 조건에 맞는 250건을 찾기 위해
테이블 전체(10만 행, 78MB)를 처음부터 끝까지 읽는다(Seq Scan) — 조건에 안 맞는 99,750건도
전부 디스크/버퍼에서 읽어야 그중 250건을 걸러낼 수 있기 때문이다. 그래서 읽은 블록 수가
9,742개(≈76MB)로 테이블 크기와 거의 같다.

부분 인덱스(`WHERE province IS NOT NULL AND city IS NOT NULL AND weather_baseline IS NOT NULL`)
는 조건을 만족하는 행의 주소만 미리 걸러 저장해 둔 것이라, 인덱스 자체가 250건 언저리
크기(448kB)로 작다. 쿼리는 그 작은 인덱스만 훑어(Bitmap Heap Scan) 필요한 행의 위치를 얻고,
그 위치로만 테이블에 접근한다. 읽는 블록이 252개(≈2MB)로 줄어드는 이유다.

**왜 하필 부분 인덱스인가(전체 인덱스가 아니라).** `date_end` 전체에 인덱스를 걸 수도 있었지만,
감시 배치가 실제로 필요로 하는 건 "끝나지 않았고 지역·기준선을 가진" 행뿐이다(전체의 0.25%).
조건 없는 인덱스는 나머지 99.75%의 항목까지 함께 유지 비용을 지불한다 — 일정을 저장·수정할
때마다 그 인덱스도 갱신되는데, 감시 대상이 아닌 행의 갱신은 버리는 비용이다. `WHERE` 절을
인덱스 자체에 넣어 두면 조건에 안 맞는 행은 애초에 인덱스에 들어가지 않아, 크기도 작고
쓰기 비용도 준다.

한 가지는 확인 후 기각했다 — "인덱스가 없으면 외부 hub 호출도 N+1로 늘어난다"는 가설을
세웠으나, 코드(`ScheduleWeatherWatcher.java:82-87`)를 보니 배치는 DB 쿼리로 이미 필터링된
250건에 대해서만 hub를 호출한다. hub 호출 횟수는 인덱스 유무와 무관하게 항상 감시 대상
수만큼이고, 느려지는 건 그 앞단 DB 쿼리뿐이다. 틀린 인과관계를 넣지 않기 위해 뺐다.

**동기 엔드포인트(폴링 제거) — 왕복 10~16회 → 1회**
§24 실기기 검증 로그에 남은 실측 추천 소요시간(28초·46초)을 근거로 삼았다. 비동기 계약
(`Retry-After: 3`)이면 완료까지 평균 10~16회 GET 폴링이 필요하지만, `/trip/replan`(동기)은
1회 POST로 끝난다. 폰의 배터리·데이터 사용에 직결되는 수치다.

**왜 이렇게 줄어드는가.** 비동기 계약은 "지금 만들어라"(POST, 202)와 "다 됐나 보자"(GET)를
분리한 설계라, 추천이 완성되기까지 걸리는 시간을 클라이언트가 직접 나눠서 반복 확인해야
한다. 서버가 `Retry-After: 3`으로 "3초 뒤에 다시 물어봐라"라고만 답을 주고, 실제로 다 되는
시점(28~46초)은 그보다 훨씬 뒤이므로 그 사이를 GET 요청으로 채우게 된다.

동기 엔드포인트는 서버 안에서 그 대기를 대신 흡수한다(`TripService.awaitDraft` 가 서버
내부에서 700ms 간격으로 최대 150초까지 Redis 를 확인) — 클라이언트가 볼 때는 한 번의 요청이
28~46초 걸려 끝날 뿐, 그 사이 아무 것도 보낼 필요가 없다. 대기의 책임을 클라이언트 왕복에서
서버 내부 루프로 옮긴 것이다. 대신 그 시간 동안 커넥션 하나를 물고 있으므로, 트래픽이 아주
많다면(동시에 수천 명이 재추천을 누르는 상황) 스레드/커넥션 점유 비용과 맞바꾼 것이라는
전제가 붙는다 — 지금 규모(폰 앱, 개인 재추천 클릭)에서는 문제가 되지 않는다.

**발견한 결함 6건:**

1. 재연결 구간의 메시지 유실 — 끊긴 사이 방송된 말이 영영 오지 않음
2. 끊긴 동안 전송이 조용히 버려짐 — 사용자는 보냈다고 인지
3. 좀비 연결 — 하트비트 수신 감시 부재
4. 재연결 몰림 — 백오프 지터 부재
5. `_teardown()`의 `await` 교착 — **방 전환 자체가 멈춤**(시험으로 발견)
6. 계층 간 누락 — 화면이 소켓 큐를 우회해 REST로 새어 나감(실기 시연으로 발견)

**한 줄 요약(이력서용 문구 초안):** *"Flutter 채팅 클라이언트에 STOMP over WebSocket
실시간 통신을 라이브러리 없이 직접 구현하고, 재연결·좀비 연결·프레임 조각화 등 장애

## 24. 날씨 변화 감지 → 저장 일정 재추천 (2026-09-02~03)

**상황:** 본선 제안서에 "날씨 변화 시 재추천"이 기능으로 적혀 있는데, 원격 저장소 네 곳의
모든 브랜치를 훑어도 구현이 없었다. 예보를 읽는 코드는 있었다 — agent 의 `fetch_weather`
노드가 추천을 만들 때 hub 에서 예보를 받아 쓴다. 그러나 그것은 **추천을 만드는 그 순간의
예보**일 뿐, 이미 저장된 일정의 예보가 나중에 달라졌는지 보는 쪽은 아무도 없었다.

**판단:** 감지(배치) · 알림 보관(스키마) · 사용자 선택(API) · 화면(배너)의 네 조각이
필요하다고 보고, 설계 결정 네 개를 먼저 사용자와 정했다.

| 결정 | 택한 쪽 | 이유 |
|---|---|---|
| 재탐색 1일 3회 한도 | **소모하지 않음** | 사용자 변심이 아니라 외부 변수가 바꾼 상황. 한도를 깎으면 손해를 사용자가 진다 |
| 서버가 코스를 자동 교체 | **하지 않음** | 비가 와도 그대로 가려는 사람이 있다. 알림만 걸고 선택은 사용자가 |
| 지난 일정 | **감시·노출·재추천 전부 제외** | 다녀온 여행에 배너가 남으면 사용자가 할 일이 없다 |
| 거절(무시) 시 기준선 | **현재 예보로 이동** | 그러지 않으면 다음 순회에 같은 알림이 다시 뜬다 |

### 24.1 구조

일정을 저장할 때 그 시점 예보를 **기준선**으로 굳히고(`schedules.weather_baseline`),
배치가 주기적으로 예보를 다시 받아 기준선과 견준다. 실내/야외 판단이 뒤집히면
(강수확률 50% 경계 또는 하늘 상태가 비·눈) `schedules.weather_alert` 에 알림을 남긴다.

| 계층 | 파일 | 역할 |
|---|---|---|
| 판정 규칙 | `weather/WeatherChangeRule.java` | 기준선 대 현재 예보. 부수효과 없는 순수 함수 |
| 조회·저장 | `weather/ScheduleWeatherService.java` | hub 호출, 기준선 생성, 알림 기록, 기준선 이동 |
| 주기 실행 | `weather/ScheduleWeatherWatcher.java` | 30분 주기(설정), 일정별 예외 격리 |
| 스키마 | `db/migration/V011__weather_replan.sql` | 컬럼 7개 추가, 감시 조건 부분 인덱스 |
| API | `TripController` · `ScheduleController` | 동기 재추천 · 비동기 재추천 · 알림 무시 |
| 화면 | `trip/widgets/weather_alert_banner.dart` 외 | 목록 배지, 상세 배너, 두 선택지 |

**지역을 두 곳에 두는 이유:** hub 의 날씨는 좌표가 아니라 지역명으로 묻는데, 그 지역명은
추천 요청에만 실려 있고 결과 payload 에는 남지 않는다. 그래서 추천 작업 행에 먼저 새기고
(`recommend_jobs.province/city`) 일정 저장 때 일정으로 옮긴다. 감시 배치가 작업 행을
거치지 않고 일정만 훑을 수 있어야 하기 때문이다.

**백필하지 않는다:** 지난 일정의 지역을 좌표로 되짚어 채우면 엉뚱한 동네 날씨로 "비 온다"고
알리게 된다. 모르는 건 모르는 채로 두고 감시에서 뺀다.

### 24.2 재추천이 날씨를 반영하지 않는 결함 — 코드를 읽다 발견

사용자가 "재추천에 날씨가 실제로 반영되느냐"고 물었을 때 확인하다 찾았다.

재추천은 저장된 조건(지역·기간·이동수단)으로 추천을 다시 요청한다. 그런데 재사용 캐시의
키는 지역·기간·테마·이동수단·예산·시간대로 만들어지고 **날씨가 들어 있지 않다.** 조건이
그대로인 재추천은 반드시 캐시에 맞고, 맞으면 agent 가 아예 돌지 않는다. agent 가 돌지
않으면 `fetch_weather` 도 돌지 않는다 — **비 오기 전 코스가 그대로 돌아온다.**

`RecommendService.createFreshRecommendation()` 을 따로 두어 캐시 조회를 건너뛰고, 결과를
캐시에 등록하지도 않도록 했다(반대 방향 오염 방지). 날씨를 요청에 싣지 않는 설계는 그대로
두었다 — agent 가 지역·기간으로 hub 에 직접 묻기 때문에, 캐시만 우회하면 **추천이 실제로
도는 시점**의 예보가 반영된다.

### 24.3 같은 알림이 되살아나는 결함 — 실스택 검증에서 발견

재추천을 끝낸 뒤 다음 감시 순회에서 같은 알림이 다시 떴다. 기준선이 저장 당시 값에 머물러
있어, 새 예보와 견주면 여전히 "바뀌었다"가 나왔다.

재추천과 무시 양쪽 모두 기준선을 현재 예보로 옮기도록 `acceptCurrentForecast()` 하나로
합쳤다. 다만 **재추천은 성공한 뒤에만** 옮긴다 — 실패한 재추천으로 알림을 지우면 사용자가
바뀐 날씨를 모른 채 옛 코스를 들고 간다.

### 24.4 앱이 못 붙는 계약 — 동기 엔드포인트 추가

처음엔 비동기(202 + `job_id` + 폴링)로만 만들었는데, 앱이 구현한 것은 동기 계약
(`/api/v1/trip/generate`)뿐이었다. 폴링 코드를 앱에 새로 넣는 대신
`POST /api/v1/trip/replan` 을 추가해 완성된 `TripGenerateResponse` 를 200 으로 돌려줬다.
generate/route 와 응답 모양이 같아 **결과 화면을 그대로 재사용**한다.

### 24.5 실기기 검증 — 격리 환경을 만들어 실행

같은 기계에서 다른 세션이 도커 스택과 백엔드를 돌리고 있었다. 그 환경을 건드리지 않고
검증하려고 격리 환경을 따로 세웠다. **락이 아니라 격리를 택한 이유**는, 배타 락은 남의
작업을 멈춰 세우는 도구여서 "영향 없이"라는 조건과 정반대이기 때문이다.

| 자원 | 격리 방법 |
|---|---|
| PostgreSQL | 같은 서버에 신규 DB `map_weather` 생성(Flyway 가 전부 새로 만듦) |
| Redis 키 공간 | 논리 DB 인덱스 분리(9~15) |
| 완료 이벤트 스트림 | 스트림은 공유하되 **컨슈머 그룹을 분리** — 같은 그룹에 들어가면 경쟁 소비자가 되어 남의 완료 메시지를 가로챈다 |
| 서버 포트 | 8085 |

검증 중 격리 구멍 세 개를 찾았다.

1. **포트 충돌** — 8081 이 비었다고 보고 띄웠으나 다른 세션 백엔드가 쓰고 있었다. 내 기동은
   바인딩에 실패했는데 `/actuator/health` 는 200 을 돌려줘 성공으로 착각했고, 그 상태로 보낸
   가입 요청이 **남의 DB 에 계정을 만들었다.** 만든 행 2개(사용자·리프레시 토큰)를 즉시
   제거했다. 이후 기동 확인은 포트 응답이 아니라 **내 로그의 `Started ServiceUserApplication`**
   으로 하도록 바꿨다.
2. **빌드 산출물 폴더 공유** — `build.gradle` 이 빌드 경로를 절대경로 하나로 고정하고 있어,
   내 컴파일이 다른 세션이 실행 중이던 클래스를 덮었다.
3. **엉뚱한 Redis** — 에이전트는 `map-service-redis`(16379)로 완료 이벤트를 발행하는데
   `map-user-redis`(6379)를 보고 있어 결과를 영영 못 받았다.

세 번을 고친 뒤 실기기(SM-S928N)에서 전 구간을 확인했다: 목록 배지 → 상세 배너 →
재추천(두 버튼 잠금 → 새 코스 6곳) → 무시(배너 사라지고 원본 유지). 서버 쪽으로도
재탐색 카운터가 생기지 않고 캐시 연결고리도 남지 않는 것을 확인했다.

### 24.6 워크트리 빌드 충돌의 근본 수정

위 2번은 이 저장소를 워크트리로 여러 개 여는 사람 누구에게나 일어난다. 증상이
"고치지도 않은 코드가 도는 것처럼 보임"이라 추적이 어렵다.

경로를 **워크트리의 절대경로에서 파생**시켜 기본값에서 갈라 두었다. 성질 세 개를 맞췄다 —
같은 워크트리는 언제나 같은 경로(결정적, 증분 캐시 보존), 다른 워크트리는 반드시 다른 경로
(단사, 경로 해시로 이름이 같은 워크트리도 구분), 다른 세션과 상의 불필요(무협의).

환경변수 옵트인으로 두지 않은 이유는 **문제를 아는 사람만 보호받는 구조**가 되기 때문이다.
정작 당하는 사람은 그 변수의 존재를 모른다.

### 24.7 다른 기기·CI 에서만 깨지는 것들 정리

PR 을 받는 쪽에서 재현될 문제를 따로 훑었다.

- **골든 이미지 시험 폐기** — 배너를 PNG 로 굳혀 두었는데, 한글 글꼴을 시스템에서 실어
  렌더링한 것이라 글꼴이 없는 기기(CI·macOS·Linux)에서는 글자가 네모로 그려져 반드시
  깨진다. 검사 대상과 무관한 이유로 갈리는 시험이라, 문구·선택지·잠금만 보는 위젯 시험
  5개로 바꿨다. 잠금은 버튼 위젯 종류가 아니라 `onPressed == null` 로 확인한다.
- **테스트 프로파일에서 감시 배치 차단** — 설정에 항목이 없어 통합 시험 컨텍스트에서 배치가
  켜져 있었다. 최초 지연 60초 안에 시험이 끝나 우연히 안 터질 뿐, 느린 기기나 CI 에서만
  재현되는 불안정이다.
- **빌드 폴더 뿌리를 시스템 드라이브에서** — `C:` 를 박아 두면 시스템 드라이브가 다른
  기기에서 깨진다. 사용자 임시 폴더는 경로에 계정 이름이 들어가 한글 계정에서 원래 문제로
  되돌아가므로 쓰지 않았다.

PR 직전 점검에서 `develop` 이 20커밋 앞서 있고 충돌 4건이 있음을 발견해 리베이스로
해결하고 올렸다. CI 는 통과했지만 **묻지 않고 히스토리를 다시 쓴 것**이 문제였다.

되돌리는 순서를 강제 푸시 없이 짰다: PR 닫기 → 원격 브랜치 삭제 → 로컬을 리베이스 이전
커밋으로 복원 → `develop` 을 **머지**로 받아 같은 충돌 4건을 같은 방식으로 해결 → 새로
푸시하고 PR 재생성. 원래 커밋 SHA 6개가 그대로 살아났다.

충돌 넷은 모두 **서로 다른 것을 더한 자리**였다 — `develop` 이 그 사이 넣은 본문 암호화
(`PayloadCipher`)와 내 지역 조회(`findRegion`)가 같은 클래스에 붙었다. 어느 한쪽을 고르는
선택은 없었고 양쪽을 모두 남겼다. 머지 후 `develop` 의 암호화 시험이 실제로 실행되는 것까지
확인했다.

**결과물:** PR [map-service-user#32](https://github.com/we-meet-trip/map-service-user/pull/32),
[map-service-client#79](https://github.com/we-meet-trip/map-service-client/pull/79) — CI 통과, 리뷰 대기.
부수 브랜치 둘(`fix/worktree-build-dir`, `docs/auth-user-global`)은 커밋만 두고 대기.

### 25.1 성능 지표 측정 방법과 원리

정성적 서술 대신 재현 가능한 두 지표를 실측했다.

**감시 쿼리(부분 인덱스) — 41배**
`idx_schedules_weather_watch`가 없을 때와 있을 때를 같은 데이터셋(PostgreSQL, 10만 건)에서
비교했다. 실제 서비스 분포를 가정한다 — 저장 일정 대부분은 이미 종료됐고(감시 대상 아님),
지역·기준선을 가진 것은 이 기능 이후 저장분뿐이다. 감시 대상을 100,000건 중 250건(0.25%)
으로 두고 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`을 각 7회 실행해 중앙값을 썼다.

| | 인덱스 없음 | 부분 인덱스 |
|---|---|---|
| 실행 시간(중앙값) | 16.0ms | 0.39ms |
| 읽은 버퍼 블록 | 9,742 | 252 |
| 접근 방식 | Seq Scan | Bitmap Heap Scan |

**왜 이만큼 차이 나는가.** 인덱스가 없으면 옵티마이저는 조건에 맞는 250건을 찾기 위해
테이블 전체(10만 행, 78MB)를 처음부터 끝까지 읽는다(Seq Scan) — 조건에 안 맞는 99,750건도
전부 디스크/버퍼에서 읽어야 그중 250건을 걸러낼 수 있기 때문이다. 그래서 읽은 블록 수가
9,742개(≈76MB)로 테이블 크기와 거의 같다.

부분 인덱스(`WHERE province IS NOT NULL AND city IS NOT NULL AND weather_baseline IS NOT NULL`)
는 조건을 만족하는 행의 주소만 미리 걸러 저장해 둔 것이라, 인덱스 자체가 250건 언저리
크기(448kB)로 작다. 쿼리는 그 작은 인덱스만 훑어(Bitmap Heap Scan) 필요한 행의 위치를 얻고,
그 위치로만 테이블에 접근한다. 읽는 블록이 252개(≈2MB)로 줄어드는 이유다.

**왜 하필 부분 인덱스인가(전체 인덱스가 아니라).** `date_end` 전체에 인덱스를 걸 수도 있었지만,
감시 배치가 실제로 필요로 하는 건 "끝나지 않았고 지역·기준선을 가진" 행뿐이다(전체의 0.25%).
조건 없는 인덱스는 나머지 99.75%의 항목까지 함께 유지 비용을 지불한다 — 일정을 저장·수정할
때마다 그 인덱스도 갱신되는데, 감시 대상이 아닌 행의 갱신은 버리는 비용이다. `WHERE` 절을
인덱스 자체에 넣어 두면 조건에 안 맞는 행은 애초에 인덱스에 들어가지 않아, 크기도 작고
쓰기 비용도 준다.

한 가지는 확인 후 기각했다 — "인덱스가 없으면 외부 hub 호출도 N+1로 늘어난다"는 가설을
세웠으나, 코드(`ScheduleWeatherWatcher.java:82-87`)를 보니 배치는 DB 쿼리로 이미 필터링된
250건에 대해서만 hub를 호출한다. hub 호출 횟수는 인덱스 유무와 무관하게 항상 감시 대상
수만큼이고, 느려지는 건 그 앞단 DB 쿼리뿐이다. 틀린 인과관계를 넣지 않기 위해 뺐다.

**동기 엔드포인트(폴링 제거) — 왕복 10~16회 → 1회**
§24 실기기 검증 로그에 남은 실측 추천 소요시간(28초·46초)을 근거로 삼았다. 비동기 계약
(`Retry-After: 3`)이면 완료까지 평균 10~16회 GET 폴링이 필요하지만, `/trip/replan`(동기)은
1회 POST로 끝난다. 폰의 배터리·데이터 사용에 직결되는 수치다.

**왜 이렇게 줄어드는가.** 비동기 계약은 "지금 만들어라"(POST, 202)와 "다 됐나 보자"(GET)를
분리한 설계라, 추천이 완성되기까지 걸리는 시간을 클라이언트가 직접 나눠서 반복 확인해야
한다. 서버가 `Retry-After: 3`으로 "3초 뒤에 다시 물어봐라"라고만 답을 주고, 실제로 다 되는
시점(28~46초)은 그보다 훨씬 뒤이므로 그 사이를 GET 요청으로 채우게 된다.

동기 엔드포인트는 서버 안에서 그 대기를 대신 흡수한다(`TripService.awaitDraft` 가 서버
내부에서 700ms 간격으로 최대 150초까지 Redis 를 확인) — 클라이언트가 볼 때는 한 번의 요청이
28~46초 걸려 끝날 뿐, 그 사이 아무 것도 보낼 필요가 없다. 대기의 책임을 클라이언트 왕복에서
서버 내부 루프로 옮긴 것이다. 대신 그 시간 동안 커넥션 하나를 물고 있으므로, 트래픽이 아주
많다면(동시에 수천 명이 재추천을 누르는 상황) 스레드/커넥션 점유 비용과 맞바꾼 것이라는
전제가 붙는다 — 지금 규모(폰 앱, 개인 재추천 클릭)에서는 문제가 되지 않는다.

**발견한 결함 6건:**

1. **재추천이 날씨를 반영하지 않음** — 캐시 키에 날씨가 없어 조건이 같은 재추천은 반드시
   캐시에 맞고, 맞으면 agent 가 돌지 않아 예보를 다시 읽지 않는다(코드 추적으로 발견)
2. **같은 알림이 되살아남** — 기준선을 옮기지 않아 다음 순회에서 같은 변화가 다시 잡힘
   (실스택 검증으로 발견)
3. **앱이 못 붙는 계약** — 비동기 202+폴링만 있어 동기 계약만 구현한 앱이 사용 불가
4. **워크트리 간 빌드 산출물 덮어쓰기** — 실제로 다른 세션이 실행 중이던 클래스를 교체함
5. **글꼴 의존 골든 시험** — 한글 글꼴 없는 기기에서 반드시 실패(CI 도입 전 제거)
6. **시험 환경에서 배치 기동** — 느린 기기·CI 에서만 재현되는 불안정

**검증 방식(면접에서 설명할 값):**

- 실기기(SM-S928N) 전 구간 확인 — 감지 → 배너 → 재추천/무시 → 기준선 이동 → 재알림 없음
- 감시 스캔 실측 **35~50초** 내 알림 생성(주기 60초 설정), 재추천 왕복 **약 40초**
- 격리 환경 구성으로 공유 인프라 무접촉 — 신규 DB · Redis 논리 DB 분리 · 컨슈머 그룹 분리
- 격리 구멍 3건을 검증 중 발견하고 원인까지 규명(포트 점유 · 빌드 경로 공유 · 다른 Redis
  인스턴스)

**한 줄 요약(이력서용 문구 초안):** *"저장된 여행 일정의 기상 예보 변화를 주기 배치로 감지해
사용자에게 재추천을 제안하는 기능을 서버·앱 양쪽에 구현했습니다. 감시 쿼리에 부분 인덱스를
설계해 10만 건 규모에서 조회 성능을 약 41배(16.0ms→0.39ms), 버퍼 읽기를 97.4% 개선했고,
비동기 폴링 계약을 동기 엔드포인트로 대체해 완료까지 평균 10~16회이던 API 왕복을 1회로
줄였습니다. 재추천이 재사용 캐시에 걸려 예보를 다시 읽지 않는 결함을 코드 추적으로 발견해
캐시 우회 경로를 분리했고, 다른 세션이 점유한 공유 인프라를 건드리지 않도록 데이터베이스·
Redis 논리 DB·컨슈머 그룹을 분리한 격리 환경을 구성해 실기기 검증을 수행했습니다."*

> **단서 — 협업 규범에서 배운 것.** PR 직전 `develop` 과의 충돌을 리베이스로 해결했다가,
> 공유될 히스토리를 사전 합의 없이 다시 쓴 것이 문제라는 지적을 받고 머지 방식으로 되돌렸다.
> 강제 푸시 없이 되돌리는 순서(PR 닫기 → 원격 브랜치 삭제 → 로컬 복원 → 머지 → 재발송)를
> 밟아 원래 커밋 SHA 6개를 보존했다. 이력서에 쓴다면 "리베이스로 정리했다"가 아니라
> **"공유 브랜치의 히스토리를 보존하는 방식으로 되돌렸다"** 쪽이 사실이다.
