## 3. 실측 결과

### 3.1 103 (수어 영상) — 라벨 확인

`[라벨]01_real_word_morpheme.zip`(0.11GB)의 정면(F) 48,000개 전수를 집계했다.

| 항목 | 실측 |
|---|---|
| 규모 | WORD 3000개 × 수행자 REAL01~16(집계상 17종) × 5시점(D/F/L/R/U). 시점당 47,994개. 시점의 뜻은 문서가 아니라 샘플 프레임 1장(WORD1501, REAL01)으로 본 추정: F=정면, D=아래에서 올려다본 각도, U=위에서 내려다본 각도, L·R=옆(비스듬한 측면) |
| 라벨 형태 | JSON 1개 = 클립 1개. `data[0]`에 `start`, `end`, `attributes[0].name`(gloss). 예: WORD0001 = "고민", 1.743~3.103초 / 영상 4.867초 |
| 수행자 ID | 파일명 `REALxx`, 폴더 `morpheme/01~16`이 대응. 수행자로 보이나 문서로 확인한 것은 아님 |
| 고유 gloss | 2,963개 (3,000 ID 중 232개 gloss가 여러 ID에 걸침) |
| 라벨 불일치 | 264개 ID는 수행자마다 gloss 표기가 다름 → 클래스 확정 전 정리 필요 |
| 결측 | F 시점 11개는 `data`가 비어 있음 |
| 단어 구간 | 중앙값 1.57초(47프레임), p95 2.7초(81프레임). 영상 중앙값 4.13초 안에서 시작 오프셋 중앙값 1.5초 |

같은 폴더에 받아 둔 다른 라벨 zip: `real_sen_morpheme`(SEN 2000문장 × 16 × 5 = 160,000개), `crowd_morpheme`(17,000개), `syn_sen_keypoint`(0.81GB). **문장·crowd·syn 데이터는 열어 보지 않았다.**

### 3.2 636 (재난 안전 정보 수어영상) — 문장-gloss 쌍

`수어스크립트_TL.zip`을 xlsx 131개로 파싱해 `pairs.tsv`(200,986블록)를 만들었다. **확장자는 `.zip`이지만 형식은 7-Zip이다.**

| gloss | 26,023종, 3,138,538토큰. 끝 숫자·`#`를 떼면 19,145종 |

**파싱 누락:** gloss/시작/종료 값 개수가 안 맞으면 그 행을 통째로 버리는 코드였다. 로그상 MISMATCH가 102개 파일, 합계 39,295건(WEATHER-1_1 한 파일이 17,365건). 위 gloss 통계는 이 누락을 반영하지 못했고, 누락 토큰 비율은 **아직 세지 않았다.**

### 3.3 MediaPipe 처리속도 벤치마크

환경: i5-1340P 16스레드, RAM 15.7GB, NVIDIA GPU 없음. 1080p 30fps 영상 각 150프레임(103·636 결과가 사실상 같음).

| 설정 | 1프로세스 fps | 4프로세스 합계 | 8프로세스 합계 |
|---|---|---|---|
| Holistic complexity 1 | 19.5 | 38~43 | 41~48 |
| Holistic complexity 0 | 24 | 37~40 | 47~50 |
| Pose+Hands 분리 (c0 / c1) | 23 / 14 | 미측정 | 미측정 |

- 병렬 효과가 작다: 8프로세스에서도 합계가 약 45fps에서 멈춤. 640폭 축소는 fps 이득이 없다(병목은 추론).
- 150프레임 짧은 측정이라 장시간 열 제한은 반영되지 않았다. 실제는 더 느릴 수 있다.

전수 재추출 예상 (합계 45fps 가정, 37~50fps면 ±20%):

| 대상 | 프레임 | 소요 |
|---|---|---|
| 103 정면(F) 전체 | 약 590만 | 약 36시간 |
| 103 정면, 단어 구간 ±0.5초만 | 약 절반 | 약 18시간 (추정, 미측정) |
| 636 전체 | 약 1억 3,400만 (샘플 27개 mp4 평균 665프레임 × 201,026) | 약 34일 (31~40일) |
| 636 전체, 15fps | 약 6,700만 | 약 17일 |

### 3.4 636 XML(OpenPose 2D) vs MediaPipe Holistic

636 샘플 27영상, 17,957프레임. 손 오차는 손목~중지 MCP 길이 대비 21점 평균, 상체는 어깨너비 대비.

| 항목 | 결과 |
|---|---|
| 손 오차 | 왼손 중앙값 0.081 / p90 0.126, 오른손 0.097 / p90 0.201 |
| 좌우 대응 | 같은 쪽끼리 0.08~0.10, 뒤바꾸면 3.6~3.9 → 좌우 규약 동일 |
| 손 점 순서 | 같은 쪽 점끼리 오차가 작음 → 21점 인덱스 동일 |
| 프레임 정렬 | 오프셋 0에서 최소(0.095), ±1이면 0.22 → 프레임 번호가 그대로 대응 |
| 상체 7점 | 어깨 0.03, 팔꿈치 0.04~0.05, 손목 0.05~0.06 (중앙값) |
| 검출 커버리지 | XML 유효 97%, MediaPipe 검출 99%, 둘 다 96~97% |
| 프레임 간 떨림 | XML 0.203, MediaPipe 0.191 (중앙값) → XML은 사후 평활·보간 데이터가 아님 |

XML 구조: CVAT 내보내기. 프레임마다 `track` 1개(`outside=0`), 라벨은 `pose_keypoints_2d`(25점, BODY_25) · `face_keypoints_2d`(70) · `hand_left/right_keypoints_2d`(21). 점은 `x,y,conf`.

## 4. 정정 — 이 기록이 대체하는 기존 주장

### 4.1 짝 문서(수어-번역-의사결정)와의 불일치

| 짝 문서의 주장 | 이 문서의 실측 | 판정 |

| 636 xml은 따로 받아야 해서 용량 추가 | 맞음. 다만 변환안에서는 xml만 받고 mp4는 안 받아도 됨 | 채택안에 유리 |

짝 문서의 "스코프 A/B/C(재난·날씨 vs 길찾기·교통 vs 병행)" 결정은 **아직 열려 있다.** 이 문서의 하위 프로젝트 D는 636 문장 쌍에 기대므로 도메인이 재난·날씨로 한정된다는 점을 인지하고 있어야 한다.

### 4.2 이 세션 안에서의 자체 정정

| 정정 | 내용 |
|---|---|
| 인덱스 비호환 | 지난 대화에서 "OpenPose와 MediaPipe 인덱스가 비호환"이라 했으나, 손 21점과 상체 대응 점은 실측으로 호환 확인. 비호환은 얼굴 쪽 점에만 해당할 가능성이 큼(얼굴은 미비교) |

## 5. A 설계 초안 (승인 대기)

**섹션 1. 통일 포맷**
- 클립(103 단어) 또는 문장(636)마다 `[T, 53, 2]` 좌표와 `[T, 53]` 검출 마스크. 좌표는 영상 크기로 나눈 0~1 값. 어깨 중심 정규화 등은 B·C 로더가 함(A는 원본 정보를 잃지 않게 둠).
- **53점** = 상체 11(코, 눈 2, 귀 2, 어깨 2, 팔꿈치 2, 손목 2) + 왼손 21 + 오른손 21. 엉덩이 2점은 사용자 결정으로 제외(§2 #8). 11점 모두 BODY_25·MediaPipe pose 양쪽에 대응이 있음. (이전 대화의 "55점"은 엉덩이를 포함한 13점 기준이라는 것이 이 세션의 추정이었음)
- **신뢰도 대신 마스크.** OpenPose 손 점에는 신뢰도가 있지만 MediaPipe 손 점에는 없음. 공통분모인 "검출 여부(0/1)"만 남기며, XML 신뢰도 0.2 미만은 미검출 처리(0.2는 이번 비교에서 쓴 값이며 튜닝한 값이 아님).
- 메타 인덱스 표: 출처, gloss 또는 한국어 문장, 수행자, 프레임 구간, 분할 라벨.

**섹션 2. 어댑터**
- `636 XML → 53점`: `outside=0` 프레임만 읽어 재배열. 좌우는 그대로(측정으로 확인). 프레임 수는 `track` 수로 셈.
- `103 mp4 → 53점`: Holistic complexity 1, **정면(F)만**(사용자 결정, §2 #9), 라벨 단어 구간 ±0.5초만 추출.
- 검증: 27샘플 비교를 회귀 검사로 남김. 손 오차가 이 수준을 벗어나면 실패.

**열린 질문**
1. ~~엉덩이 2점~~ → **결정: 제외, 53점** (§2 #8).
2. **636 수행자 ID(§6)**
3. ~~103의 5시점 처리~~ → **결정: 정면(F)만 사용, 나머지 4시점은 쓰지 않음** (§2 #9). 나중에 실제 웹캠에서 정확도가 떨어지면 위에서 내려다본 U 시점(노트북 웹캠 각도에 가까울 수 있음)을 증강으로 추가하는 것을 다시 검토할 수 있음.

## 6. 열린 위험 · 미검증

| 항목 | 상태 |
|---|---|
| 636 수행자 독립 분할 | 수행자 ID를 확인한 곳은 형태소 JSON의 `signer.id`(샘플 27개는 전부 signer 87 한 명). 그 JSON 다운로드가 정체. xlsx·XML·파일명에 수행자 정보가 있는지는 열어 보지 않았으므로 먼저 확인하는 것이 대안 |
| 정체된 다운로드 | Innorix 프로세스는 살아 있으나 진행 없음. 사용자가 창 확인 필요 |
| XML 변환의 일반화 | 비교는 수행자 1명(signer 87), 카테고리 1개(COLDWAVE), 27영상. 다른 조건에서도 같다는 보장 없음 |
| 좌표 일치 ≠ 인식 정확도 | 좌표 불일치를 잰 것이지, XML로 학습해 MediaPipe 입력에서 정확도가 유지되는지는 B·C 단계에서만 확인 가능. 완화책: 636 일부를 MediaPipe로도 추출해 검증용 보관 |
| 미비교 | 얼굴 점, 깊이(z) |
| 103 단어/문장 속도 차 | 103 단어 중앙값 47프레임 vs 636 단어(문장 속) 중앙값 약 16프레임. 두 데이터셋의 속도 척도가 3배 가까이 다름 |
| 103 문장·crowd·syn 데이터 | 열어 보지 않음. C에 쓸 수 있는지 미확인 |
| 학습 연산 | NVIDIA GPU 없음(Intel Arc A350M 4GB). B·C 학습은 별도 위험 |
