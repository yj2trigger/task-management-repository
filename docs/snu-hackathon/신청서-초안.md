## 1. 신청서 항목 (제출용 문안)

### 3-1. 아이디어 / 서비스 (권장 500자 이내, 약 500자)

> 흰냥이는 하루 종일 화면을 보는 IT 직장인·개발 학습자의 PC 구석에 사는 고양이입니다(웹 기술 기반 Windows 앱). 할 일 앱은 내가 정리해야 하고 AI 비서는 내가 물어봐야 하지만, 흰냥이는 던져 주기만 하면 됩니다. 공부 파일·링크·"10/31 시험" 같은 일정을 고양이에게 먹이처럼 끌어다 놓으면 기억해 두었다가, 하루 패턴(집중 시간대, 연속 작업 시간)과 합쳐 "정규화 5일째 안 봤어, 20분만 하자냥" 하고 지금 할 일 하나를 먼저 제안하고 [열기] 버튼으로 파일까지 열어 줍니다. 90분째 앉아 있으면 기지개를 권하고, 도와준 뒤엔 칭찬을 조릅니다. 거절하면 이유를 기억해 다음 제안이 바뀝니다. AI(Croche)는 먹인 정보 중 필요한 기억만 골라 쓰고, 파일 열기 같은 앱 기능을 정해진 규칙 안에서 실행하며, 제안을 고양이 말투로 전합니다.

### 3-2. 지속 가능성 / 사업화 방향 (권장 300자 이내, 약 290자)

> 1차 사용자는 IT 직장인·개발 학습자·수험생입니다. 내가 먹여 기른 정보가 쌓일수록 나에게 맞는 고양이가 되어 다른 앱으로 옮기기 어렵고, 애정도·레벨 성장이 매일 켜 둘 이유가 됩니다. 수익은 B2C는 기본 무료 + 고양이 종류·꾸미기·주간 리포트 구독, B2B는 기업 웰니스 프로그램 인원당 월 구독입니다. 이후 팀 고양이, 모바일 연동으로 확장합니다.

### 3-3. Croche 활용 계획 및 필요한 AI 기능 (권장 500자 이내, 약 500자)

> Croche를 흰냥이의 AI 담당으로 씁니다. 고양이 앱은 웹 기술(Electron) 기반 Windows 앱으로 Croche SDK에 연결합니다. [Runtime] ① 기억·맥락 관리: 먹인 파일·일정·거절 이력 중 지금 추천에 필요한 것만 골라 써서 토큰을 아끼고 고양이 성격을 유지합니다. ② 앱 기능 연결: 파일·링크 열기, 눈 쉬기 시작, 기지개 동작, 먹이 등록을 정해진 규칙 안에서 실행합니다. ③ 별도 백엔드 없이 앱+Croche로 구동합니다. [Studio] 거절 많은 사용자·밤샘형 사용자 같은 가상 사용자로 "거절 학습이 실제로 추천을 바꾸는지" 평가하고, 비용 대시보드와 모델 비교로 말풍선용 모델을 고릅니다. [제안] (a) 기억 열람·삭제와 로컬 저장 옵션 (b) 대화에서 일정을 제목·날짜로 뽑는 구조화 추출 (c) 데스크톱(Electron/Python) 공식 지원 (d) 앱이 먼저 말 거는 proactive 호출.

글자 수는 대략치다. 제출 전 폼에서 직접 세어 본다.

## 2. 데스크톱 앱이 가능한가

런타임 기능 기준으로 플랫폼 제약은 없어 보인다.

| 런타임 기능 | 플랫폼 의존? | 데스크톱에서 |
|---|---|---|
| 기억·맥락 관리 | 아니오 | 문제 없음 |
| 백엔드 불필요 | 아니오 (모바일도 Croche 클라우드 호출 구조일 것) | 동일 |
| 앱 기능 연결 | 앱 코드 쪽 | 파일 열기는 브라우저·모바일 샌드박스에서 막히지만 데스크톱은 가능 |

### 실제 위험

| 위험 | 내용 | 대응 |
|---|---|---|
| SDK 언어 | 기반이 JS/TS(Node). Python(tkinter)에서 직접 호출 보장 없음 | 고양이 앱을 **Electron(JS/TS)**으로 만든다 |
| 도구 실행 위치 | 앱 기능 연결을 Croche 서버가 실행하는지, 앱이 콜백으로 실행하는지 미확인 | 아래 §3의 우회 설계로 위험을 낮추고, OT·메일로 확인 |
| 제출 규정 | 데스크톱 제출 불허 가능성 | 메일로만 해소 |

### 권장 구성
- Electron 한 앱: 투명·항상 위 창 + `shell.openPath` 파일 열기 + Croche SDK
- 관찰자(활성 창·입력 횟수)·SQLite: Node 라이브러리 또는 Python 별도 프로세스(로컬 HTTP로 연결). 3일 개발에는 언어 하나가 안전하나 Python 경험을 살리는 병행도 가능 — 팀에서 결정

## 3. 도구 실행 위치 우회 설계

전제: 모바일 앱에서 Croche가 동작하는 방식 그대로 쓴다. 모바일 앱도 로컬 파일을 직접 열 수 없고, "아이템 지급·예약" 같은 도구는 앱이 가진 기능이다. 그렇다면 Croche가 *무엇을 할지 결정*하고 앱이 *실제로 실행*하는 구조가 기본이라고 볼 수 있다. 흰냥이도 같은 구조로 만든다.

| 단계 | 하는 곳 | 내용 |
|---|---|---|
| 1 | 앱(로컬) | 먹이 등록 시 `food_id`·제목·과목·마감일만 Croche에 알리고, **파일 경로는 로컬 SQLite에만 보관** |
| 2 | Croche | 기억·맥락으로 추천 결정 → 액션 호출 `open_file(food_id=12)` (또는 구조화된 응답 `{action:"open_file", id:12}`) |
| 3 | 앱(로컬) | `food_id → 경로`를 로컬 DB에서 찾아 `shell.openPath`로 실행 |

효과:
- Croche가 도구를 서버에서 실행하는 방식이어도, 최악의 경우 "구조화된 응답을 앱이 해석해 실행"으로 우회된다.
- 남는 확인 사항: 앱 기능 연결이 콜백 방식인지, 구조화 응답만 가능한지는 OT에서 보면 된다. 어느 쪽이든 설계는 같다.
