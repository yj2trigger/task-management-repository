# 환경 제약과 극복 방법 (프로젝트 목표의 하나)

> 작성: 2026-09-20. 프로젝트 목표(사용자 발언 2026-09-20): **우리 데이터·모델·하드웨어·시간·전처리·학습 환경에서 생기는 한계와 제약을 조사하고, 극복 방법을 찾아낸다.** 이 결과는 신청서의 **예상 산출물 중 하나**로 적는다("제약을 실측·정리해 극복 방법을 알아낸다").
> 이 문서는 (1) 지금까지 **이미 확인한 제약**과 (2) 각 제약의 **극복 후보와 검증 상태**를 한 표로 모은 것이다. 프로젝트 내내 갱신한다.
> 근거 수준: **실측** = 이 프로젝트에서 직접 측정·열람 / **계산** = 실측값으로 계산 / **자료** = 초기 검토 자료의 제안(검증 안 함) / **공식 확인** = 공식 문서를 직접 열어 확인 / **검색 요약** = 검색 결과 요약만 봄(공식 문서 미확인) / **추정** = 근거 약함.
> 극복 상태: **검증됨** = 효과를 이 프로젝트에서 확인 / **후보** = 아직 안 해 봄 / **기각** = 해 봤는데 효과 없음.

---

## 1. 이 목표를 어떻게 수행하나 (신청서에 쓸 방법)

제약마다 다음 다섯 칸을 채운다. 매주 활동보고서에서 갱신하고, 최종보고서에 "환경 제약과 극복" 장으로 넣는다.

| 칸 | 내용 |
|---|---|
| 제약 | 무엇이 안 되는가(수치로) |
| 원인 | 왜 그런가(하드웨어·데이터·방법 중 무엇) |
| 극복 후보 | 시도해 볼 방법 |
| 시도 | 실제로 한 것 |
| 결과 | 효과(수치)와 남은 한계. 효과가 없으면 "기각"으로 남긴다 |

**이미 이 방식으로 한 예(사전 준비 현황):** MediaPipe 입력 해상도를 640폭으로 줄여 재 봤더니 **속도 차이가 없었다**(병목이 디코딩이 아니라 추론) → 기각으로 기록. Pose와 Hands를 분리한 구성도 22.9 fps로 Holistic complexity 0(24 fps)보다 이득이 없었다 → 기각. complexity 0으로 바꾸는 것은 24 fps로 약 23% 빨라 **검증됨**.
