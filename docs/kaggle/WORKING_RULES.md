## 1. 블로그 6항목을 정확한 제목 그대로 쓴다

대회 규칙이 요구하는 6항목을 **제목 그대로, 하나도 빠짐없이** 쓴다.

1. 💡 이번에 세운 가설 또는 시도한 접근
2. 🔧 방법
3. 💻 사용한 코드
4. 📊 결과 분석
5. 📚 배운 점 또는 막혔던 점 — "배운 점"만 쓰면 안 된다. "또는 막혔던 점"까지 포함해야 한다
6. 🎯 다음 시도 계획

**왜:** Day3 정리 중 ⑤를 "배운 점"으로 줄여 쓰고 ⑥을 통째로 빠뜨려 지적받았다. 6항목이 다 있어야 그날 포인트가 인정된다.
**어떻게:** 블로그 콘텐츠를 쓰거나 덧붙일 때마다 6개 제목을 원문 그대로 체크리스트처럼 확인하고, 마지막에 빠진 것이 없는지 다시 본다.

## 2. 실험 결과는 항상 파일로 저장하고, 파일명으로 구분한다

모델 비교·튜닝·피처엔지니어링 같은 실험 코드는 `print` 로 끝내지 않는다. 결과를 json/csv 로 저장하고, 파일명에 **언제(타임스탬프) + 무슨 실행인지**를 넣는다(예: `results_20260812_2130_feature_eng.json`). 같은 이름으로 덮어써서 이전 실행이 사라지면 안 된다.

**왜:** Day3에서 노트북에 준 코드가 print 만 하고 저장을 빠뜨려 지적받았다. Day2에서도 "이전 버전을 제출해야 할 때 다시 학습시키느라 시간이 아깝다"는 이유로 같은 합의를 한 적이 있다.
**어떻게:** 학습·비교·튜닝 코드를 새로 쓰거나 복사해 줄 때마다 끝에 `json.dump(...)` 또는 `to_csv(...)` 를 기본으로 넣는다. 사용자가 지적하기 전에 넣는다.

## 3. 소요 시간도 숫자로 남긴다

성능 지표(AUC/RMSLE 등)뿐 아니라 걸린 시간도 재서 결과 json 에 같이 저장한다. "빠르다/오래 걸린다"가 아니라 초 단위 숫자로 남긴다.

**왜:** Day4에서 Day3(RandomForest 38분)과 이번(XGBoost·LightGBM·CatBoost 10~25초)을 견주다가, 나중에 참고하려면 속도도 정량 기록이 필요하다는 요청을 받았다. 모델 종류에 따라 데이터 규모 대비 학습 시간이 극명하게 갈리는 것이 Day3~4에서 반복 확인됐다.
**어떻게:** 실험 스크립트에 `time.time()` 측정을 기본으로 넣고 결과 json 에 `elapsed_sec` 필드를 항상 포함한다. 대회 노트(`day-0X_notes.md`)의 결과 표에도 시간 컬럼을 넣는다.

## 4. 리더보드보다 자체 검증지표를 믿는다

외부 리더보드 점수와 자체 검증지표가 충돌할 때, **소수 4자리 이하의 작은 차이는 자체 지표를 믿는다.** 리더보드를 근거로 판단을 뒤집는 것은 **0.0n 규모의 큰 차이**일 때만 한다.

**왜:** public LB 는 test 의 일부(예: 33%)로만 계산되므로 작은 차이는 표본 변동일 수 있다. 자체 검증은 설계를 우리가 알고 통제할 수 있다.
**어떻게:**
- LB 차이 0.0005 수준 → 무시하고 자체 지표로 고른다
- LB 차이 0.0n 수준 → 자체 검증 설계에 결함이 있다고 보고 원인을 찾는다
- 자체 지표가 틀렸다면 지표를 고치는 것이 우선이지, LB 로 갈아타는 것이 아니다

Day10에서 CV 0.045 대 LB 0.072(격차 0.027)는 검증 설계 결함으로 인정했지만, 연도계수 선택에서 LB 차이 0.00046은 무시하고 자체 교정검증을 따랐다.

## 5. 유의기준은 모든 선택에 적용한다

실험 전에 유의기준(significance threshold)을 고정했다면 **모든 선택**에 적용한다. 모델 비교나 피처엔지니어링 판정뿐 아니라 앙상블 가중치, 혼합비율, 임계값 스윕까지 포함한다.

**왜:** Day8에서 혼합비율 w=0.6/0.7/0.8 이 0.924972/0.924976/0.924968 로 나왔는데 "0.7에서 정점"이라고 썼다. 최대-최소 차이 0.000008 은 유의기준 0.000326의 40분의 1이었다. 스스로 세운 규칙을 어기고 잡음을 신호로 읽은 것이다.
**어떻게:** 스윕 결과에서 최고값을 고르기 전에 최대-최소 차이를 유의기준과 먼저 견준다. 기준 미만이면 "전부 동급"이라고 말하고 방향성만 주장한다("혼합이 낫다"까지는 되지만 "7:3이 최적"은 안 된다). 후보를 N개 비교했다면 선택 편향이 있으므로 기준선을 `× (1 + log(N)/3)` 정도로 올려 잡는다.

## 6. 더 나은 결과가 나오면 "지금 제출하세요"까지 말한다

이전 제출·기준보다 확실히 나은 결과가 나오면 완료 사실과 수치만 보고하지 않는다. **"이게 지금까지 최선이니 바로 제출하세요"** 같은 실행 항목으로 끝맺는다.

**왜:** Day3에서 `submission_ensemble_lgb_rf.csv`(RMSLE 1.0567, 당시 최고)가 완성됐는데 "완성됨"이라고만 보고하고 다음 작업으로 넘어갔다. 한참 뒤 "그거 제출했나요?"라고 물어서야 실행 가능한 최선이었다는 게 드러났다.
**어떻게:** 결과 보고에 (1) 이전 최고와 견줘 개선됐는지 명시하고, (2) 개선됐다면 다음 행동을 구체적으로 제안한다. 여러 실험이 동시에 도는 상황일수록 놓치기 쉽다.

## 7. 네이버 블로그는 표와 코드블록이 다르게 붙는다

마크다운 표(`| 헤더 | … |`)를 네이버 블로그 에디터에 붙이면 테두리 있는 실제 표로 자동 변환된다. 반면 코드블록(```) 안의 아스키 표(confusion matrix 등)는 변환되지 않고 줄바꿈까지 깨진다.

**왜:** Day1 블로그를 쓰다가 사용자가 직접 붙여 보고 확인한 사실이다.
**어떻게:** 표 형태 데이터는 마크다운 표로 준다. 코드나 아스키아트는 소스코드 버튼을 쓰거나 네이버 표 기능으로 직접 만들라고 안내한다.
