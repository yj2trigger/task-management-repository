# ic-pbl 키오스크(CLI판) — GUI+CLI 미러링 실제 구현과 버그 수정 규율

> 출처: 세션 `41de03ec-79ce-4d59-81ac-0577302f2ca0`(`c:\onedrive\_대학교\프로그래밍기초\icpbl\ic-pbl 프로그램` 폴더, 2026-05-12). `ORIGIN-요구사항결정-2026-05-11.md`(전날 세션)에서 논의만 되고 미확정으로 남았던 "CLI + GUI 연동 시연 버전"을 실제로 구현한 세션.

## 아키텍처가 계획과 달라진 지점

기원 세션(2026-05-11)에서는 **`logger` 콜백 패턴**(비즈니스 로직이 선택적으로 logger 함수를 받아 호출)으로 GUI-터미널 연동을 구현하기로 잠정 결정했었음. 그런데 실제 구현 시점에 사용자가 요구를 구체화하면서 설계가 바뀜:

> "정확히는 지금의 코드가 최대한 수정되지 않고 GUI를 위한 추가적인 코드만 생성하는 방향을 원해요."

이 요구에 맞춰 Claude가 심문(AskUserQuestion 스타일)으로 확인한 뒤 채택한 **최종 방식은 logger 콜백이 아니라 subprocess 표준입출력 주입**:

```
gui.py (신규 파일, main.py는 3줄만 수정)
├── subprocess.Popen("python -u main.py", stdin=PIPE, stdout=PIPE)
├── 왼쪽 65%: 카페 키오스크 UI(터치 버튼, 상품·옵션·장바구니 이미지 포함)
│   ├── stdout을 정규식으로 파싱해 현재 화면 상태 감지 → 버튼 자동 전환
│   └── 버튼 클릭 시 subprocess의 stdin에 "1\n" 같은 문자열을 실제로 주입(키 입력을 흉내)
└── 오른쪽 35%: 터미널 에뮬레이터 UI(검정 배경, 고정폭 폰트) — stdout 실시간 미러링
```

**결정 근거가 된 사용자 요구 4가지**(Claude의 확인 질문에 대한 답):
1. 실행 구조: 배포 상태에서도 GUI 터치 → CLI 입력처럼 보여야 함, 반드시 진짜 터미널일 필요는 없음
2. 입력 전달: 실제 키스트로크 주입(Controller 직접 공유 방식 대신)
3. 화면 구성: 카페 키오스크처럼 실제 상품/옵션/장바구니가 보여야 함(숫자 버튼만은 안 됨)
4. 오른쪽 "CLI처럼 보이는 창"은 tkinter 안의 터미널 에뮬레이터로 충분(실제 cmd 창일 필요 없음), 왼쪽 GUI는 이미지·색상 있는 수준을 원함

`cli_view.py`는 `_show_idle()`에서 `msvcrt.getch()`(콘솔 전용 키 입력 대기)를 파이프 stdin에서도 동작하도록 3줄만 바꿔 최소 침습으로 유지.

## 구현 중 발견한 버그 2건 (인코딩 + 상태 감지)

최초 실행 시 "화면만 뜨고 상호작용이 안 됨" → 원인 2가지 동시 발견:
1. **인코딩 문제**: subprocess stdout이 Windows 기본 인코딩(CP949)으로 나오는데 GUI는 UTF-8로 디코딩을 시도해 한글이 영원히 실패, 화면에 아무것도 안 나옴.
2. **idle 화면 감지 버그**: 대기 화면은 프롬프트 패턴 없이 끝나서 상태 큐(`screen_q`)에 이벤트가 안 올라와 GUI가 idle 상태 전환을 못 알아챔.

## 버그 수정 작업 방식 — "먼저 계획 문서화, 승인 후 1건씩" 규율

사용자가 다섯 가지 버그를 한 번에 나열하며 명시적으로 작업 순서를 지정함:
> "다음의 작업들을 바로 해결하기 시작하지 말고, 계획을 세워서 문서에 저장하세요. 이후에 제가 승인하면 해결을 진행하고 현재상황을 기록하면서 해결해나가세요. 한가지를 해결했으면 승인을 받은 다음에 다음 작업으로 넘어가세요."

이에 따라 `docs/gui_fix_plan.md`를 먼저 작성 — 5개 버그의 근본 원인을 표로 정리하고 **원인의 파급 범위(다른 버그와 겹치는 정도)를 기준으로 권장 수정 순서(5→2→1→3→4)를 재배열**함(사용자가 나열한 순서 그대로가 아니라, "관리자 메뉴 종료 버튼 누락"의 원인인 정규식 파싱 결함이 다른 항목에도 영향을 주는 공통 원인이라 우선 배치). 예: 정규식이 `re.match`(줄당 첫 항목만 인식)라서 "1. 재고 보충  2. 상품 ON/OFF"처럼 한 줄에 옵션 여러 개가 있으면 뒤 항목을 놓치는 게 여러 버그의 공통 원인이었음 → `re.finditer`로 교체.

## TDD 규율 재확인 — 버그 재현 테스트 → 수정 → 회귀 테스트만 남기고 정리

이후 다른 GUI 버그 2건에서 사용자가 시스템적 디버깅 절차를 다시 명시적으로 요구:
> "unittest를 만들고 test한 다음 해결하고 다시 테스트하세요. 만약 수정 전 unittest로 문제임이 확실해졌다면 수정해서 해당 unittest를 기준으로 통과할 때까지 가설 설정, 코드 개선, 테스트를 반복하세요"

실행 순서: (1) 버그를 **증명하는** 테스트 작성(`test_gui_bugs.py`, BUG-01/02) → 실행해 실제로 재현됨을 확인 → (2) 원인 수정(각각 1줄 변경: 비밀번호 입력 모드에서 뒤로가기 버튼 생성 조건 누락 / `_send()`가 stale 타이머를 리셋 안 해 0.3초 유예 없이 바로 발화) → (3) 수정 후 재실행해 버그 재현 테스트가 반대로 뒤집히는 것 확인 → (4) **버그 재현용 테스트는 역할이 끝났으므로 제거하고, 회귀 방지용 FIX 테스트만 남김**(216/216 PASS). 이 마지막 단계("증명용 테스트는 지우고 회귀용만 남긴다")가 이 프로젝트의 테스트 관리 관행으로 확립된 지점.

**자가 진단 요구**: 사용자가 "문제 해결을 스스로 판단할 수 있는 방법을 알아내세요"라고 요구한 지점도 있음 — GUI가 실제로 무엇을 subprocess에 보내는지, CLI가 어떻게 반응하는지를 subprocess 레벨에서 직접 관찰하는 자가 진단 방법을 그 자리에서 고안하도록 요구받음(사용자가 매번 재현 여부를 보고해주는 것에 의존하지 말라는 의미).

## 이 문서가 메우는 공백

기원 문서(ORIGIN-요구사항결정)에는 GUI+CLI 연동이 "logger 콜백 패턴"으로 계획된 것으로만 남아 있었는데, **실제 구현은 그와 다른 subprocess stdin/stdout 주입 방식**으로 실현됐음 — 이 문서가 그 설계 변경과 실현 과정을 보완함.
