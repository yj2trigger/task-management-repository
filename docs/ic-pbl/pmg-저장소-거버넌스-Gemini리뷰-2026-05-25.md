## 배경

팀(`yj2trigger/pmg-ic-pbl`) 저장소에 (1) PR 없이 아무나 `develop` 브랜치에 직접 push할 수 있는 상태였고, (2) PR 코드리뷰를 자동화할 방법이 필요했음. 사용자가 후보 방법(GitHub Actions + Gemini 1.5 Flash, 무료 티어 활용)을 미리 조사해와서 그 적용을 요청.

## 브랜치 보호 규칙 적용

GitHub API로 직접 확인한 결과 **두 브랜치 모두 보호 규칙이 전혀 없는 상태**(`protected: false`)였음. 적용한 정책:

| 브랜치 | PR 필수 | 승인 필요 수 | 관리자 bypass | Force push |
|---|---|---|---|---|
| `main` | ✅ | 1명 | 허용 | 차단 |
| `develope`(오타, 아래 참조) | ✅ | 1명 | 허용 | 차단 |

흐름: `feature/* → develope`(PR+승인1) → `develope → main`(PR+승인1). 관리자는 두 브랜치 다 직접 push 가능하게(`enforce_admins: false`) 열어둠 — 팀 프로젝트에서 관리자 편의와 일반 팀원 강제 사이의 절충.

**"develope" 오타 발견**: 사용자가 "push는 항상 main 브랜치에 진행되나요?"라고 묻는 과정에서 실제 브랜치명이 `develop`이 아니라 **`develope`**(오타)로 만들어져 있었음을 GitHub API 조회로 발견. 세션 종료 시점엔 수정 여부 미확정(브랜치 이름 변경 시 보호 규칙이 자동 이전된다는 점만 안내) — **이후 문서에 남은 `develope`라는 표기가 있다면 이 오타가 원인**.

## Gemini 자동 PR 리뷰 워크플로우

**최초 설계**: `.github/workflows/gemini-review.yml` — PR이 열리거나 갱신될 때 base와의 diff를 추출해 Gemini 1.5 Flash API로 보내고, 결과를 PR 댓글로 자동 게시. 무료 티어 한도(분당 15회, 일 1,500회) 안에서 충분하다고 판단. diff가 50,000자를 넘으면 앞부분만 잘라 보내는 안전장치 포함.

**배포 위치 실수와 즉시 수정**: 사용자가 "제가 main에 파일 생성했어요"라고 알려왔을 때 확인해보니, 워크플로우 파일이 **`workflows/gemini-review.yml`**(레포 루트 바로 아래)에 생성돼 있었음 — GitHub Actions는 **`.github/workflows/`** 경로만 인식하므로 이 상태로는 전혀 동작하지 않았음. 올바른 위치에 새로 생성하고 잘못된 위치의 파일은 삭제해 해결.

**이후 실패(이 세션 밖)**: 기존 `docs/ic-pbl` 커밋 로그에 남은 "ARG_MAX 초과로 인한 gemini-review 실패"는 이 세션 이후 실제 PR에서 diff가 너무 커서(설계 당시 50,000자 컷 로직이 있었음에도) 셸 명령줄 인자 길이 한도(ARG_MAX)를 넘겨 터진 것으로 보이며, 그 진단·수정은 별도 세션에서 이뤄짐(이 문서 범위 밖).
