## 배경 — 이 세션이 만든 것

사용자가 매우 상세한 프롬프트("당신은 Python 소프트웨어 아키텍트... 분석 → 질문 → 사용자 승인 → 다음 단계 순서로만 진행하라")로 시작. 이 프롬프트 자체가 이후 ic-pbl 전체 개발 방식원형이 됨:
- STEP 1(요구사항 분석) → STEP 2(사용자 심문) → STEP 3(용어사전) → STEP 4(구현범위) → STEP 5(시스템흐름) → STEP 6(아키텍처) → STEP 7(테스트전략) → STEP 8(승인요약) → STEP 9(코드작성)
- 코드는 절대 먼저 쓰지 않고, 각 STEP마다 사용자 승인을 받아야 다음으로 진행

## 원래 과제 — Coffee/Gummy 마이크로팩토리 키오스크

**STEP 1~2 — 질의응답으로 확정된 핵심 결정들 (Q1~Q31)**

**아키텍처 결정 — CLI 우선, GUI는 나중** (2026-05-11T09:27Z, 세션 중 가장 중요한 구조 결정)

사용자: "구현할 때 gui가 아니라 터미널에서만 진행할 수 있도록 하고 이후에 gui로 넘어가기 편하도록 구현하세요."

- Business Logic 계층은 View(CLI든 GUI든)가 무엇인지 절대 모르게 설계 — "블랙박스 함수"(Q2)의 실제 구현 방법으로 재해석됨.
- 이후 사용자가 "CLI로 먼저 제출하고, 시연 때는 GUI 클릭 → 터미널에 미러링되는 연동 버전도 보여주고 싶다"(Q29)고 구체화 → GUI와 터미널을 **threading으로 양방향 동기화할지, 단방향(GUI→터미널 로그만)으로 할지**가 쟁점이 됨.
- 최종 결정(Q30): **단방향**(GUI 클릭 → 터미널에 로그 출력만, 터미널에서 입력은 안 받음) — threading 없이 안정적으로 구현 가능하다는 이유로 채택. `logger` 콜백 패턴(비즈니스 로직이 옵션으로 logger 함수를 받아 호출)으로 구현.
- 제출물은 CLI 버전만(Q31, "변경될 수도 있음"이라는 유보 조건 붙음).

**JSON 파일 구조 — 사용자가 직접 통합을 제안한 사례**

STEP 3 용어사전에서 처음엔 `sales_stats.json`과 `ingredient_stats.json`을 분리 제안했으나, 사용자가 "따로 할 이유가 있을까요?"라고 되물음 → 분리/통합 근거를 표로 비교(통합 근거: 갱신 시점이 항상 동일해 분리 시 두 파일 간 불일치 위험, 파일 수 감소, 원자성) → 사용자 승인으로 `stats.json` 하나로 통합 확정. 최종 JSON 파일 8개(`products`, `ingredients`, `recipes`, `options`, `change_reserve`, `stats`, `discount_policy`, `admin_config`).

**문서 분리 요청** (2026-05-11T09:47Z): "requirements에 있는 용어사전, 구현범위, 시스템 흐름, 아키텍처를 다른 파일들로 분리하세요" → `requirements.md`(STEP1~2만) / `terminology.md` / `scope.md` / `system_flow.md` / `architecture.md` 5개로 분리. **이 분리 구조가 지금 `docs/ic-pbl/`에 남아있는 파일 구성 그대로**임 — 즉 현재 문서 트리의 기원이 이 시점.

## STEP 9 진입 — 개발 방법론 자체가 바뀐 지점 (2026-05-11T10:18Z)

사용자가 두 번째 대형 프롬프트를 투입, "Micro Incremental TDD"라는 별도 방법론을 명시적으로 도입:
- **핵심 원칙**: 한 번에 최소 단위(클래스 1개 또는 함수 3개 이하)만, 테스트 먼저, 추정 금지, 매 단계 승인, **문서가 유일한 진실**(코드가 아니라 `requirements.md` 등 문서 6종이 기준).
- **`CURRENT_STATE.md` 규칙 도입**: "AI는 기억에 의존하지 않는다" — 세션마다 이 파일을 읽어 현재 Unit·완료 Unit·Blocker·다음 작업을 복구하는 방식. **이것이 지금 `docs/ic-pbl/CURRENT_STATE.md`의 존재 이유**이자, 이 task-management-repository 자체가 채택한 "문서로 상태를 이어간다"는 철학과 같은 계통.
- **STEP A~F**(Unit 선정 → 테스트 설계 → 최소 구현 → 테스트 작성 → 실행 검증 → 상태 요약)라는 세부 루프가 이때 확정되고, 이후 모든 코드 작업이 이 루프를 따름.

**UNIT-01 (exceptions.py) 실제 구현**: leaf node(다른 모든 모듈이 import하지만 자신은 아무것도 의존하지 않음)라는 이유로 첫 Unit으로 선정 → `KioskException` + 하위 예외 6종 정의, 테스트 16개 전부 통과 확인 후 세션 종료.
