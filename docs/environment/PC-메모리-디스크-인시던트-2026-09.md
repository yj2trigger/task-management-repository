## 3. graphify 훅 버그 (별도 원인, 수정 완료)

**증상**: 매 턴 끝마다 `graphify update .`가 백그라운드로 뜨는데, 겹쳐 쌓이며 프로세스당 최대 ~8GB를 먹음.

**원인 (소스로 확인)**:
1. WSL에서 Miniconda 설치 파일을 받을 때 `curl -O`를 실수로 저장소 폴더(`map-service-user`) 안에서 실행 → `Miniconda3-latest-Linux-x86_64.sh`(188.8MB)가 저장소 루트에 남음
2. graphify가 `.sh`를 코드로 취급해 통째로(`read_bytes`) 파싱 — 크기 상한 없음. 셸 스크립트 머리말 뒤에 188MB 바이너리가 붙은 형식이라 파싱에 수 GB 소모
3. 이 파일은 git에 추적도 무시도 안 돼서 "바뀐 파일"로 매번 잡히고, `graph.json`은 갱신이 안 끝나 계속 "낡은" 상태로 남아 매 턴 재시도 조건이 계속 참이 됨

**조치**:
| 파일 | 변경 | 이유 |
|---|---|---|
| 저장소 루트 | `Miniconda3-latest-Linux-x86_64.sh` 삭제 | 근본 원인 파일. WSL 안 conda는 이미 설치돼 있어 불필요 |
| `~/.claude/hooks/graphify-stop-update.mjs` | 잠금 파일에 자식 PID 저장, 그 프로세스가 살아있으면 새로 안 띄움 (숫자 아니면 기존 2분 시간 잠금) | 갱신이 2분보다 오래 걸려 매 턴 새 프로세스가 쌓이던 문제 |
| 같은 파일 | `hs_err_pid*.log`, `replay_pid*.log`를 "변경 판정"에서 제외 | 이 파일들이 항상 `graph.json`보다 새 파일로 잡혀 매 턴 재실행되던 원인 |
| 같은 파일 | `GRAPHIFY_MAX_WORKERS=1` 설정 + 낮은 우선순위 | 병렬 작업자 수 기본값이 CPU 스레드 전부라 그만큼 메모리가 곱해지던 것 방지 |
| 같은 파일 | 가용 메모리 8GB 미만이면 이번 턴은 갱신 자체를 안 띄움 | 최후 안전장치 |

**검증한 것**: `node --check` 문법 통과, PID 잠금이 실제로 새 PID(16712)를 기록하는 것 확인.
**검증 못 한 것**: 워커 1개로 줄여도 실측 약 8GB를 썼다는 정황(작업자 문제가 아니라 대용량 파일 파싱 자체가 원인이었다는 뜻) — 파일 삭제 후 재실행해서 메모리가 실제로 줄었는지는 확인 안 함.

## 4. 구조적 리스크: 외장 SSD 의존

Android SDK를 D(외장 SSD)로 옮기고 C 경로에 정션(`mklink /J`)을 연결하는 방식을 씀. **SSD가 분리되면 정션이 빈 곳을 가리켜서 Android Studio·Flutter 빌드가 전부 막힘.** 09-20~09-21에 실제로 2회 재발 확인.

| 항목 | 위치 | SSD 없으면? |
|---|---|---|
| Android SDK | D (정션 경유) | Studio, Flutter Android 빌드 전부 실패 |
| `Ubuntu-LeRobot` (WSL) | D | 실행 자체가 안 됨 |
| `.gradle`, `.android`(adb 키 등), Chrome 프로필 | C (이동 안 함, 공용이라 위험 판단해 보류) | 영향 없음 |

**원칙("Studio만 SSD, 나머지는 SSD 없이")에 따라 정리된 현재 방침**:
- Android SDK, LeRobot 환경은 SSD 필수로 유지
- 수업용 등 SSD 없이도 써야 하는 WSL은 **별도로 C에 새로 설치**해서 분리 (`wsl --install -d Ubuntu`, 기본 배포판은 `docker-desktop` 그대로 유지 — VS Code에서 "Connect to WSL using Distro..."로 매번 명시 선택 필요)

**미해결**: SSD가 왜 자주 빠지는지(케이블/포트/절전 설정) 원인 미확인.

## 5. 재발 시 확인 순서

1. 작업 관리자에서 CPU/메모리 열 정렬해서 실제 최상위 프로세스 확인 (이번에 "보이는 프로세스 합쳐도 26%인데 전체 97%" 착시를 겪음 — 반드시 정렬해서 볼 것)
2. `graphify` 관련 python.exe가 떠 있는지, `graphify-out/.stop-update.lock`의 PID가 살아있는지 확인
3. 저장소 루트에 실수로 받아진 대용량 파일 없는지 (`git status`의 untracked 큰 파일)
4. 외장 SSD(D) 연결 여부 — `Get-Volume -DriveLetter D` 또는 파일 탐색기
5. pagefile.sys 크기 — 비정상으로 크면(20GB+) "다시 시작"(완전 재부팅, "시스템 종료"는 빠른 시작 때문에 pagefile 안 줄어듦)
