## 1부 — "Cannot create temporary file in ...Temp: Permission denied"

**배경**: Claude가 링크드리스트 과제(`insert`, `delete`, `size` 등)를 학생 코드 스타일로 구현 완료 후, 컴파일로 검증하려 했으나 Claude의 Bash/PowerShell 도구에서부터 `gcc`가 임시 파일을 못 만듦.

**Claude 쪽 진단(도구 사용 제한)**: `-pipe` 플래그로 임시파일 자체를 우회 시도, `TMPDIR`/`TMP`/`TEMP` 환경변수를 프로젝트 폴더로 바꿔 시도 — 전부 실패. `icacls`로 Temp 폴더 자체는 쓰기 가능함을 확인했는데도 gcc는 계속 거부됨 → "sandbox가 CreateFile API를 차단하는 것으로 보임"이라고 잠정 결론(Claude Code 자체의 Bash 실행 샌드박스 제한).

**사용자 자신의 터미널에서도 동일 오류 재현**: Claude 도구 제한 때문이 아니라, **사용자의 일반 cmd.exe·관리자 권한 cmd에서도 100% 동일한 오류**가 남 → 이 컴퓨터의 Temp 폴더 자체에 문제가 있다는 뜻으로 진단 방향 전환.

**진짜 원인 발견**: `icacls`로 확인한 결과 사용자 계정(`rexro`)은 Temp 폴더에 Full Control을 갖고 있었음(ACL 자체는 정상). 하지만 폴더 ACL 목록에 **`CodexSandboxUsers`라는 낯선 그룹**이 붙어 있었음 — OpenAI Codex CLI가 이전에 설치되면서 자신의 샌드박스용으로 시스템 Temp 폴더의 ACL을 건드려 놓은 흔적으로 추정. `icacls ... /remove "yegu\CodexSandboxUsers"`로 제거를 시도했으나 이후에도 gcc 오류는 그대로 재현됨 — **완전한 근본원인 규명까지는 도달하지 못함**(Temp ACL 문제라는 심증은 있었지만 그 제거만으로는 안 풀림).

**실질적 해결(원인 규명 대신 우회)**: 근본 원인을 계속 캐는 대신, **MinGW를 통째로 새로 설치**하는 쪽으로 전환:
1. 기존 설치(`C:\env_coding\env_ver1\x86_64-15.2.0-...`)는 그대로 둔 채 winlibs.com에서 **GCC 16.1.0** 최신판을 새로 받음
2. 사용자가 용량 문제로 기존 설치를 삭제 요청 → `rmdir /s /q`로 제거
3. 새 gcc가 실제로 풀린 위치를 여러 번의 `dir` 삽질 끝에 특정(`C:\env_coding\env_ver1\winlibs-x86_64-posix-seh-gcc-16.1.0-mingw-w64ucrt-14.0.0-r2\mingw64\bin`) — 압축 해제 위치가 사용자가 예상한 곳(Downloads)이 아니라 다른 폴더였음
4. 시스템 PATH를 이 새 경로로 교체 → 새 CMD 창에서 `gcc --version` 확인 성공 → 컴파일·실행까지 성공, 출력이 예상 트레이스와 정확히 일치함을 확인하고 종료

**교훈**: "Temp 폴더 Permission denied"는 폴더 자체 ACL만 볼 게 아니라, **그 ACL에 낯선 그룹(다른 개발도구가 심어둔 것)이 끼어 있는지**까지 봐야 함. 이번 건은 그 그룹을 지워도 안 풀려서 결국 재설치로 우회했고, 진짜 원인이 그 그룹이었는지는 끝내 확인되지 않음(미해결로 남은 부분).

## 2부 — 그 직후, VSCode가 새 gcc를 못 찾음

1부가 22:53에 끝나고 2분 뒤(22:55) 다른 폴더(JARAM)에서 새 세션이 시작됨 — 같은 사람이 이번엔 **VSCode 통합 터미널**에서 같은 컴파일을 시도.

**증상**: 일반 `cmd.exe`에서는 되는데(1부에서 막 고친 상태) VSCode 터미널에서는 `gcc`를 못 찾음.

**진단**:
1. `where gcc`/`pwd`이 VSCode 터미널에서 실패 → 재시작해도 동일.
2. `echo %PATH%`로 보면 새 MinGW 경로가 **PATH엔 이미 포함**돼 있음 — 그런데도 `where gcc`는 실패.
3. **근본 원인**: 그 PATH 항목을 `dir`로 직접 확인하니 `지정된 경로를 찾을 수 없습니다`. VSCode가 갖고 있는 PATH는 **1부에서 재설치하기 전, 옛 MinGW 위치**를 가리키는 유령 경로였음.
4. 결론: 1부에서 시스템 PATH를 갱신했지만, **VSCode 프로세스 자체는 그 전부터 이미 켜져 있어서 옛 PATH를 상속한 채** 계속 실행 중이었음. `Reload Window`는 설정 파일만 다시 읽을 뿐 이미 떠 있는 프로세스의 환경변수 자체는 갱신하지 않아 리로드로도 해결 안 됨.

**해결책 (3가지 중 택1로 제시, 세션 종료 시점엔 미확정)**:
- **A.** VSCode 완전 종료 후 재시작(간단하지만, 상위 프로세스인 탐색기까지 옛 환경을 물고 있으면 안 될 수도 있음)
- **B.** `settings.json`에 `terminal.integrated.env.windows`로 새 경로를 직접 박아넣기(가장 확실, PATH 상속 문제를 완전히 우회)
- **C.** 재부팅(모든 프로세스가 새 PATH를 상속하도록 강제)

## 전체 교훈

- **환경변수를 시스템 레벨에서 바꿔도, 이미 실행 중이던 프로그램에는 안 먹힌다.** 특히 VSCode처럼 오래 켜두는 프로그램은 재부팅 전까지 옛 PATH를 계속 물고 있을 수 있음. `Reload Window` ≠ 프로세스 환경변수 갱신.
- **`where <cmd>`가 실패하는데 `echo %PATH%`엔 경로가 있다면, "PATH 문자열에 있다"와 "그 경로가 실제로 존재한다"를 구분**해서 `dir <path>`로 직접 확인해야 함 — 이번 사고에서 1부·2부 둘 다 같은 유형의 유령 경로 문제였음(1부는 CodexSandboxUsers로 인한 접근 거부, 2부는 재설치로 이미 사라진 옛 경로).
- **한 개발 도구(Codex CLI)가 시스템 전역 리소스(Temp 폴더 ACL)를 건드려 놓으면, 그 도구를 안 쓰는 다른 작업(C 컴파일)에서도 원인 불명의 오류로 나타날 수 있음** — 낯선 오류를 만나면 최근에 설치한 다른 개발도구들의 흔적(ACL, 환경변수, 그룹 멤버십)도 의심해볼 것.
